# Orchestration lessons for Workflow

| Incident | Workflow requirement | Stream |
|---|---|---|
| A run can own an unbounded number of resources, so copying all cleanup outcomes into one bounded teardown event can prevent the terminal lifecycle notification from being written. | Keep complete per-resource outcomes in the durable run record; emit a bounded teardown summary with outcome counts, full sampled failure identities, and an exact omission count. Consumers that correlate outcomes read the record. | x204-kb-runner-cutover-readiness |
| A run-token match can identify a supervising caller or keeper ancestor as a cleanup candidate if that descriptor is inherited or ownership history is too broad. | The single signal boundary protects the keeper's identity and current ancestor chain independently of ownership matches, and records each signal's PID, start identity, and ownership reason; the token is held only across the command's ExtraFiles boundary. | x204-kb-runner-cutover-readiness |
| A test-only cleanup helper directly signaled a recorded keeper PID without applying the proc caller/ancestor rail, killing the test process during helper replacement. | Test cleanup and deliberate keeper-loss actions use the same record-derived signal owner as production; the recorded keeper PID has a distinct Go type, and the owner refuses caller/ancestor identities with attribution. | x204-kb-runner-cutover-readiness |
| A latest-tag waiter had no appearance deadline when a launcher failed before writing its run record, so a typo or failed launch could block orchestration indefinitely. | A waiter bounds how long it waits for the first matching durable run record, reports typed not-found with a next step, and keeps the run-completion wait separate after the record appears. | x204-kb-runner-cutover-readiness |
| A process exited between Darwin's process-tree snapshot and governor metric read; a zero-length `kern.proc.pid` result became EIO and failed admission of an unrelated heavy run. | Treat a process that disappears during metric sampling as unavailable on every supported OS, while preserving real inspection errors and their errno. | x212 round 7 |
| An admitted outside test could write stdout/stderr until its timeout, filling runner disk and forcing whole-file reads into memory. | Every supervised test output stream has a hard byte ceiling, bounded retained head/tail, and process-tree cancellation when the ceiling is exceeded. | x212 round 8 |
| A devkit selector chose package dependents for tracked changes while task keys omitted package-owned files outside declared globs and transitive dependency content. | Cache validity mirrors selection from one ownership map: hash all tracked unowned files globally, every tracked file owned by the task package locally, and all tracked files in its transitive workspace dependency closure. Preserve generated dependency outputs, ignore untracked files, and hash current working-tree contents for modified tracked files. | x183 round 18 |
| Lease integration tests launched real runners against ambient host PSI; parallel hosted `go test -race ./...` exceeded the CPU pressure threshold before child readiness. | Process-admission integration tests supply a typed deterministic host-resource source through the same admission owner, and separately verify pressure rejection and its diagnostic. | x217 round 4 |
| A fixed teardown discovery deadline could expire shortly after SIGTERM and leave an already-attributed process owner live; dead Linux task states can also retain a readable PID/start identity. | At the cleanup deadline, revalidate and escalate every already-signalled owned identity; process liveness treats zombie/dead states as non-live and reports state in teardown regressions. | x217 round 4 |
| A launcher or keeper can die while detached descendants survive outside its process group, and a nested run can inherit an outer run-token descriptor. | Keep one durable run marker across the complete descendant environment; on Linux recover marker-bearing post-start identities through the shared pidfd signal owner, stop at nested run markers, and have a keeper observe launcher death through a pipe whose write end is owned only by the launcher. | x217 round 9 |
| The journey toolchain cache key omitted the generated Node base image, so a policy change could reuse an image built from the old Node runtime. | Include every structured toolchain build input from its owning generated policy in the image identity, and mutate each policy input in a regression test while keeping Dockerfile text fixed. | x222 round 10 |
| Run-record readers selected live or finished files independently, and Linux keeper-loss recovery could signal a recorded process while missing its detached descendants when marker discovery did not return them. | One run-record location owner resolves IDs across state transitions and restores a missing ready record before cleanup reads it. Linux recovery unions marker matches with live descendants of recorded PID/start identities, filters by run start and nested-run ownership, excludes zombies, and signals through the shared pidfd owner. | x217 round 10 |
| Journey batch built the affected workspace with devkit's implicit `NumCPU-1` concurrency while candidate verification measured runner CPU and memory; batch also redirected the build stream, hiding progress and resource evidence during a hosted runner communication loss. | All hosted workspace-build callers use one measured CPU/memory concurrency owner and expose periodic resource samples with build output, so admission policy and runner evidence cannot drift by workflow. | x236-batch-shared-build |
| Workflow SSE registered its event listener after reading the initial run snapshot, so a fast worker transition in between was permanently lost; failed-only replay also kept failed job status and source-run identities while resetting steps. | Subscribe before reading the snapshot and deliver buffered events after the snapshot; replayed runs receive fresh run/job/step identities and job states derived from the reset steps, so queued work is executable and every run can reach a terminal state. | x239-workflow-runs-reach-terminal |
