# ADR-0001: Steward — персональный PM/CRM как tool-слой для агентов

**Date:** 2026-08-14
**Status:** Proposed
**Deciders:** KB Labs Team
**Last Reviewed:** 2026-08-14
**Tags:** [plugin, architecture, storage, agents]

## Context

Пользователь ведёт десятки проектов параллельно. Боли:

- держать в голове статус, ссылки и архитектуру десятков проектов;
- не забывать обещания людям («обещал Иванову прислать X два месяца назад»);
- быстро понимать, к кому идти по проблеме N в проекте Y, включая fallback, если основной контакт недоступен;
- единая карточка проекта: репо, dev/prod стенды, Grafana, Jira, архитектура — вместо «вспоминать по пяти вкладкам».

Цель — заготовка под персональный control-центр: «секретарь с бесконечной памятью и без усталости».

Ключевое ограничение: это **не UI-инструмент для ручного ведения заметок** (эта ниша закрыта Obsidian/Notion), а **data/tool-слой для AI-агентов**. Пользователь общается с агентом, агент дёргает функции плагина как инструменты и получает детерминированные структурированные ответы.

Данные для наполнения уже существуют физически — в личных сообщениях Telegram и в заметках. Проблема реальна, не гипотетическая.

## Decision

### 1. Плагин полностью самостоятельный

Никакой зависимости от `mind` (RAG) или других плагинов — соответствует duck-typing правилу монорепы. Импорты — только `@kb-labs/sdk`, никаких внутренностей платформы (`core/platform`, `core/plugin-runtime`) и никаких импортов из соседних плагинов.

### 2. Детерминированность вместо RAG

Все ответы — прямые query/CRUD-функции по структурированным данным. Агент должен получать предсказуемый ответ, а не «похожий, но не тот». RAG сознательно отложен (см. раздел «Отложено»).

### 3. CLI — это tool-поверхность агента, а не отладочный интерфейс

Платформа генерирует MCP-инструменты из `cli.commands` манифеста. Следствия, обязательные к соблюдению:

- гранулярность команд диктуется удобством агента, а не человека: несколько узких команд вместо одной с десятью флагами;
- вывод машинно-читаемый по умолчанию (структурный `CommandResult<T>`), человеческое форматирование — поверх;
- `describe` и `examples` в манифесте — это промпт, от которого зависит выбор инструмента агентом, а не хелп для человека.

Референс философии и стиля — `plugins/inbox` (атомарные примитивы, структурный JSON, вся логика классификации на стороне агента).

### 4. Вся бизнес-логика в `core`, `entry` — тонкий потребитель

```
plugins/steward/
  contracts/   типы + zod-схемы, зависимость только на zod
  core/        вся бизнес-логика, единственный источник истины
    src/functions/
      project.ts     getProject, listProjects, addResource
      person.ts      addPerson, updatePerson (+ дедуп на write-пути)
      company.ts     addCompany
      routing.ts     whoToContact
      commitment.ts  addCommitment, listCommitments, reschedule/drop/done
      event.ts       appendEvent, listEvents
      topic.ts       справочник тем с алиасами
      review.ts      getDailyReview, checkIntegrity
      export.ts      exportSnapshot
  entry/
    src/manifest.ts       cli.commands + cron.schedules + jobs + artifacts
    src/cli/commands/*.ts тонкие адаптеры → core
```

- `contracts` — plain interface для доменных моделей, zod + `z.infer` для всего, что пересекает границу (входы команд). Паттерн из `plugins/qa/src/contracts`.
- `entry` не импортирует `IDocumentDatabase` напрямую — только через `core`.
- CLI-хендлеры не содержат бизнес-условий: парсинг флагов → вызов `core` → форматирование.

### 5. Хранилище — `IDocumentDatabase` через SDK

Не Mongo напрямую. Платформа абстрагирует Mongo/Postgres/SQLite за единым интерфейсом; в проде — Mongo, для тестов доступен sqlite без переписывания логики. Коллекции автонеймспейсятся (`steward__projects`), доступ гейтится permissions манифеста.

Коллекции: `projects`, `resources`, `people`, `companies`, `project_members`, `commitments`, `events`, `topics`.

Индексы: `resources.projectId`, `commitments.status+remindAt`, `project_members.personId+projectId`, `events.subject.id+at`.

### 6. Модель данных

**Project** — центральная сущность-хаб, но **не обязательный foreign key**: `projectId?` опционален везде, где это осмысленно.

**Resource** — универсальный attachment на проект. `type` — свободная строка (repo / dev-stand / prod-stand / dashboard / jira / doc / ...). `url?` и `content?` могут быть заданы вместе или по отдельности: одна сущность покрывает и внешнюю ссылку, и хранимый в системе markdown.

**Person** — глобальный контакт. `contacts` (каналы с приоритетом), `companyId?`, `globalTopics: string[]` — сквозные компетенции, актуальные из любого проекта.

**ProjectMember** — связь Person ↔ Project: `role`, `topics?` (компетенции в контексте проекта), `priority: number` для fallback-цепочки.

**Company** — тонкая сущность `{id, name}`. Без company-level функциональности, но **форма связи `Person.companyId` фиксируется сразу** (см. «Миграционная политика»).

**Commitment** — обещание человеку с мягким сроком, отдельно от формальной задачи. `status: open | done | dropped`, `remindAt?`, `snoozedUntil?`, `staleAfterDays?`.

**Event** — сквозной append-only лог. Это то, что делает память «бесконечной»: без него система знает состояние, но не историю, и ответить «что происходило с проектом за три месяца» или «почему мы это отложили» невозможно.

```ts
Event {
  id, at
  kind: 'commitment.rescheduled' | 'commitment.dropped' | 'project.status_changed' | 'note' | ...
  subject: { type: string; id: string }   // полиморфная ссылка
  reason?: string
  text?: string
  meta?: Record<string, unknown>
}
```

Ссылка полиморфна намеренно: появление новых сущностей не меняет схему событий.

**Topic** — справочник тем с алиасами. Нормализация на записи, не на чтении.

**Task** — типизирован в `contracts`, не реализован (см. «Скоуп»).

#### Ретеншен событий

Механизм заимствуется у платформенной политики логов (`LogRetentionPolicy`, `core/platform/src/adapters/log-persistence.ts`): max age на класс записи, чистка по `deleteOlderThan`, и главный принцип — дефолты применяются всегда, рост не бывает неограниченным. Логи там и так лежат документами в `IDocumentDatabase`, то есть абстракция та же.

Отличие, которое требует инверсии дефолтов: логи — расходная диагностика, а `Event` здесь **и есть память**. Удаление `commitment.dropped` вместе с его `reason` уничтожает ровно ту способность ответить «почему отложили», ради которой лог заведён. Поэтому классы задаются не по severity, а по природе события:

| Класс | Что попадает | Max age |
| --- | --- | --- |
| `semantic` | решения, причины, заметки, жизненный цикл обещаний, смены статусов проектов | не удаляется |
| `derived` | сгенерированные review, прогоны `checkIntegrity`, отметки экспорта | 90 дней |
| `trace` | трассировка backfill-импорта, служебные касания записей | 14 дней |

Класс выводится из `Event.kind`, отдельного поля не требуется. Чистка едет на уже существующей суточной джобе — отдельный `cleanupIntervalMs` не нужен.

Если однажды объём `semantic` станет проблемой, правильный ответ — сжатие (свёртка старых событий в периодические summary), а не удаление. Но это за горизонтом MVP.

### 7. Routing: `whoToContact(topic, projectId?)`

Гибрид: при наличии `projectId` приоритет у `ProjectMember.topics` этого проекта, сортировка кандидатов по `ProjectMember.priority` (она же fallback-цепочка); затем — `Person.globalTopics` по всем контактам.

Темы матчатся через справочник с алиасами. Это критично: детерминированный поиск поверх неконтролируемого словаря хуже нечёткого — он уверенно отвечает «никого», когда в базе лежит «фронтенд» вместо «фронт».

### 8. Дедупликация — на write-пути

`addPerson` сам возвращает предупреждение о похожей записи, а не отдельная команда `findOrSuggestDuplicate`, которую агент может не вызвать. Не hard-constraint: жёсткая ошибка на дубль хуже совета, когда записи создаёт агент, а не человек. Критично для массового ввода (см. «Backfill»).

### 9. Артефакты и фоновые джобы

Через `cron.schedules` + `jobs` манифеста, отдельный демон не нужен — workflow-engine сканирует манифесты сам.

- `daily-review` (1×/сутки) → `getDailyReview()`: просроченные обещания, ближайшие сроки, застоявшиеся записи. Первой строкой — `last successful backup: N days ago`, чтобы молчаливый отказ бэкапа стал шумным.
- `export-backup` (1×/сутки) → снапшот всех коллекций → git commit + push в приватный репозиторий.

Артефакты объявляются полем `artifacts[]` манифеста и пишутся в `.kb/steward/` (`reviews/YYYY-MM-DD.md`, `exports/`). Markdown выбран не для читаемости, а как будущий корпус для штатной файловой индексации `mind` — без связанности между плагинами.

Доставка и уведомления — ответственность платформы, не плагина.

### 10. Бэкапы

Экспорт по крону → git commit + push в **приватный** репозиторий через существующий github-плагин / git-команды workflow (working dir указывается явно). Секреты — в `.env`, отдельного механизма не требуется.

Экспорт содержит PII (контакты людей, содержание договорённостей). Приватность репозитория — инвариант, не опция: он не должен попасть в публичный или командный remote.

Дополнительно `checkIntegrity()`: резкая просадка количества документов день-к-дню без явного bulk-delete поднимается в daily review, а не проглатывается в лог.

`mongodump` и инфраструктурный бэкап самой БД — уровень хоста, вне ответственности плагина.

### 11. Backfill

Первое, что произойдёт с системой — массовый разовый ввод существующих данных из Telegram и заметок: пользователь отдаёт агенту куски переписки, агент извлекает сущности и раскладывает по командам.

Требования, вытекающие из этого:

- **идемпотентность** — заливка идёт порциями, куски пересекаются; отсюда обязательность дедупликации на write-пути;
- **схема должна устояться до массового ввода** — перевводить вручную дорого; это аргумент за минимальный набор полей на запись.

Постоянный автоматический синк **не проектируется**: источника для него сейчас нет, проектировать от воздуха незачем.

## Скоуп

**В MVP:** Project, Resource, Person, ProjectMember, Company (тонкая), Commitment, Event, Topic.

**Типизировано, не реализовано:** Task.

**Вне MVP:**

- REST API — единственным потребителем мог быть Studio или MCP, но Studio не делаем, а MCP генерируется из CLI. Роуты без потребителя не окупают gateway/авторизацию/тесты. Добавляется позже без переделки `core`.
- Studio-страницы.
- RAG / семантический поиск.
- Интеграции с внешними системами (Jira/Grafana хранятся ссылками, не синхронизируются).

### Миграционная политика

Правило для документной БД: **добавить коллекцию или опциональное поле — бесплатно; изменить форму существующей связи — дорого.**

Отсюда два разных решения по отложенным сущностям:

- `Task` откладывается целиком — появится новой коллекцией, переписывать нечего.
- `Company` **не откладывается как форма связи**: вариант «строкой в `Person`» потребовал бы позже переписать все документы Person и вручную расклеить свободные строки («Сбер» / «Сбербанк» / «ПАО Сбербанк») в сущности. При множестве компаний это неприятная ручная работа с неоднозначностями. Поэтому `Person.companyId?` + тонкая коллекция вводятся сразу, функциональность наращивается позже.

Тот же принцип — причина полиморфной ссылки в `Event`.

## Consequences

### Positive

- Агент получает предсказуемые структурированные ответы вместо «похожих».
- Плагин ничего не знает о соседях: связь с агентами только через генерируемый платформой MCP.
- Смена СУБД не требует переписывания логики.
- `Event` даёт историю и «почему» бесплатно для всех сущностей сразу.
- Формы связей зафиксированы до массового ввода данных.

### Negative

- Ручной ввод — единственный канал наполнения; система деградирует, если пользователь перестанет диктовать. Осознанный риск: автоматического источника сейчас нет.
- Свободный `Resource.type` и словарь тем требуют дисциплины на записи.
- Класс `semantic` в `Event` по определению не чистится — рост медленный, но неограниченный. Сжатие в summary откладывается до появления реальной проблемы.
- Отсутствие REST закрывает интеграции извне до момента, когда его добавят.

### Alternatives Considered

- **RAG через `mind`** — отклонено: структурированные данные полностью закрываются детерминированными запросами, а прямая интеграция создала бы связанность между плагинами. Путь на будущее — экспорт markdown в директорию, которую `mind` индексирует штатно.
- **Свой демон для крон-джоб** — отклонено: `cron.schedules` в манифесте достаточно.
- **Ручной MCP-адаптер в плагине** — отклонено: платформа генерирует инструменты из манифеста; ручной путь потребовал бы завязки на внутренности `plugins/agents`.
- **Task и Company в MVP** — Task отложен как безболезненно добавляемый; Company оставлена в форме связи по миграционным соображениям.

## Implementation

1. Скаффолдинг трёх пакетов через `.claude/skills/kb-labs-create-plugin/`, референс структуры — `plugins/inbox` и `plugins/qa`.
2. `contracts`: доменные интерфейсы + zod-схемы входов команд.
3. `core`: функции поверх `IDocumentDatabase`, `ensureCollection` с индексами при инициализации.
4. `entry`: манифест (`platform.requires: ['documentDatabase']`, permissions на коллекции, `cli.commands`, `cron.schedules`, `jobs`, `artifacts`) + тонкие CLI-хендлеры.
5. Джобы `daily-review` и `export-backup`.
6. Тесты: бизнес-кейсы — в `core`, для CLI — только маппинг вход→вызов→формат вывода.

Решение пересматривается, когда появится реальный источник для автоматического ingestion либо потребность в семантическом поиске по свободному тексту.
