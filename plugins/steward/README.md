## Overview

Steward is a data/tool layer for AI agents managing dozens of parallel projects on behalf of one person: project status and links, who to contact about what (with a fallback chain), promises made to people that shouldn't be forgotten, and a full history of what happened and why.

It is **not** a UI note-taking tool — that niche is already covered by Obsidian/Notion. Every command returns deterministic, structured `CommandResult<T>` data instead of a RAG-style "similar, but not quite" answer, because an agent needs a predictable response, not an approximate one. The platform generates MCP tools directly from the CLI command manifest, so the CLI *is* the agent's tool surface, not a debugging interface for humans.

See [ADR-0001](docs/adr/0001-steward-design.md) for the full design rationale.

---

## Features

- **Projects** — status, description, and a card view bundling every attached resource and member
- **Resources** — free-form attachments per project (repo, dev/prod stand, dashboard, doc, ...), by URL and/or stored markdown content
- **People & companies** — global contacts with per-channel priority, thin company records, and duplicate detection that warns instead of blocking (agents write in bulk during backfill)
- **Project members** — person↔project links with a role and a `priority` fallback order
- **Routing (`who`)** — hybrid lookup: project-scoped competencies first (ordered by fallback priority), then global competencies across every contact, matched through a topic dictionary with aliases
- **Commitments** — promises to people with a soft deadline, snooze/drop/done lifecycle, and automatic staleness detection
- **Events** — an append-only, polymorphic history log behind every entity; this is what makes "what happened with X, and why" answerable
- **Topics** — a routing dictionary with aliases, normalized on write
- **Daily review** — stale commitments, upcoming reminders, active projects, and days since the last successful backup, generated by the `daily-review` cron job as a markdown artifact
- **Backup snapshot** — a full JSON dump of every collection, generated daily by the `export-backup` cron job

## Commands

All commands accept `--json` for structured output. Full flag reference: `kb steward <command> --help`.

### Project

| Command | Description |
|---------|-------------|
| `kb steward project add --name=... [--status] [--description]` | Create a new project |
| `kb steward project get <idOrName>` | Get a project card: status, resources, and members |
| `kb steward project list [--status]` | List projects, optionally filtered by status |
| `kb steward project update <id> [--status] [--description]` | Update a project's status or description |

### Resource

| Command | Description |
|---------|-------------|
| `kb steward resource add <projectId> --type=... --label=... [--url] [--content]` | Attach a resource to a project (repo, dev-stand, dashboard, doc, ...) |
| `kb steward resource list <projectId>` | List resources attached to a project |

### Person / Company / Member

| Command | Description |
|---------|-------------|
| `kb steward person add --name=... [--topics] [--company]` | Add a contact — returns a `possibleDuplicates` warning, not an error, on a name match |
| `kb steward person update <id> [--name] [--topics] [--company]` | Update a contact's name, topics, or company |
| `kb steward person get <idOrName>` | Get a contact by id or exact name |
| `kb steward person list` | List every known contact |
| `kb steward company add --name=...` | Add a company (thin — just a name to link people to) |
| `kb steward company list` | List companies |
| `kb steward member add --person=... --project=... --role=... [--topics] [--priority]` | Link a person to a project with a role and fallback priority |
| `kb steward member list <projectId>` | List members of a project, ordered by fallback priority |

### Routing

| Command | Description |
|---------|-------------|
| `kb steward who <topic> [--project]` | Find who to contact about a topic. With `--project`, project-scoped members take priority (fallback chain); otherwise matches global competencies across every contact |

### Commitment

| Command | Description |
|---------|-------------|
| `kb steward commitment add --text=... [--person] [--project] [--remind-at] [--stale-after-days]` | Record a promise made to a person, with an optional soft reminder date |
| `kb steward commitment list [--status] [--project] [--stale-only]` | List commitments, optionally only the stale (overdue, unsnoozed) ones |
| `kb steward commitment done <id>` | Mark a commitment fulfilled |
| `kb steward commitment drop <id> --reason=...` | Cancel a commitment — reason is required and recorded in history |
| `kb steward commitment snooze <id> --until=... [--reason]` | Postpone a commitment's reminder without cancelling it |

### Event

| Command | Description |
|---------|-------------|
| `kb steward event add --subject-type=... --subject-id=... [--text] [--kind]` | Record a manual note against a project, person, or commitment — the primary tool for backfill import |
| `kb steward event list [--subject-type] [--subject-id] [--kind]` | Read the history log for a subject — "what happened with X" |

### Topic

| Command | Description |
|---------|-------------|
| `kb steward topic add --name=... [--aliases]` | Register a topic with aliases in the routing dictionary — do this deliberately, not automatically |
| `kb steward topic list` | List the topic dictionary |

### Review

| Command | Description |
|---------|-------------|
| `kb steward review` | Daily summary: stale commitments, upcoming reminders, active projects, and days since the last successful backup |

## Configuration

No plugin-specific configuration. Steward only requires a `documentDatabase` adapter to be configured on the platform (see `platform.requires` in the manifest) — any adapter implementing `IDocumentDatabase` works (Mongo in production, SQLite/in-memory for local/test).

---

## Scope

Steward is deliberately self-contained and CLI/MCP-only for the MVP:

- **No REST API** — the only potential consumer would be Studio or MCP, and MCP is generated from the CLI manifest automatically. Can be added later without touching `core`.
- **No Studio pages** — same reasoning.
- **No RAG / semantic search** — every answer is a deterministic query/CRUD function; RAG is intentionally deferred (see ADR-0001 §"Отложено").
- **No external integrations** — Jira/Grafana/etc. are stored as `Resource` links, not synchronized.

## Permissions

Steward requires `documentDatabase` access to the following collections (see `combinePermissions()` in `entry/src/manifest.ts`):

| Category | Scope | Reason |
|----------|-------|--------|
| `documentDatabase` | `projects` | Project records |
| `documentDatabase` | `resources` | Attachments per project (repo, stand, dashboard, doc, ...) |
| `documentDatabase` | `people` | Global contacts |
| `documentDatabase` | `companies` | Thin company records |
| `documentDatabase` | `project_members` | Person↔project links with fallback priority |
| `documentDatabase` | `commitments` | Promises with soft deadlines |
| `documentDatabase` | `events` | Append-only history log |
| `documentDatabase` | `topics` | Routing dictionary with aliases |

Collections are namespaced by the platform as `steward__<name>`. Steward also declares two cron-scheduled jobs (`daily-review`, `export-backup`) that write artifacts under `.kb/steward/` — see the manifest's `artifacts[]` and `jobs.handlers[]`.

**Layout**

```
  contracts/   # zod schemas + domain types (request/response shapes)
  core/        # pure business logic, single source of truth (testable in isolation)
```


- Business logic: `core/src/functions/*.ts`
- CLI commands: `entry/src/commands/*.ts`, wired in `entry/src/manifest.ts`
