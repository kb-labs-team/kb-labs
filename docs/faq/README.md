## CLI, конфигурация и пути

### FAQ-PATH-001 — команда неожиданно использует не тот CLI или конфиг

- **Симптом:** поведение команды не соответствует изменённому исходному коду или локальной конфигурации.
- **Проверить:** `pnpm -s kb <command>` запускает CLI текущего workspace; `node ./cli/bin/dist/bin.js <command> --json` позволяет явно вызвать собранный workspace-бинарь. `kb` из `~/.local/bin` относится к установленной платформе.
- **Диагностика:** сначала зафиксировать cwd и путь бинаря; затем посмотреть `platformRoot` и `projectRoot` через `kb config show --json`. Не выводить целиком `.env` или секретные поля конфига.
- **Решение:** использовать локальный workspace CLI и убедиться, что нужные пакеты пересобраны. Не подменять установленный `kb` symlink’ом на dev build.
- **Статус:** проверено.

## Исполнение команд и workers

### FAQ-RUNTIME-001 — worker выполняет устаревший код или диагностика показывает чужой процесс

- **Симптом:** поведение handler’а расходится с текущими исходниками; в списке процессов есть несколько `worker-script.js` из разных checkout’ов.
- **Причина:** список процессов сам по себе не показывает, какой worker обслужил конкретный запрос. Пулы могут принадлежать разным платформам и долго жить независимо друг от друга.
- **Проверить:** для конкретного запроса сопоставить `requestId`, `workerId`, PID и путь `workerScript` в структурированных debug-логах. Путь штатного worker’а вычисляется относительно модуля `@kb-labs/plugin-execution-factory`; не определять его перебором каталогов или только по совпадению имени процесса.
- **Решение:** проверять checkout и сборку именно того execution backend, который указан в логах запроса. Не завершать посторонние workers и сервисы без необходимости.
- **Профилактика:** при старте worker-pool писать через `logger.debug` worker ID, PID, путь скрипта и тип транспорта; при выполнении — request ID и безопасные метаданные маршрутизации.
- **Статус:** диагностические поля добавлены; проверено на локальном запуске Agents.

## LLM и capabilities

### FAQ-LLM-001 — worker сообщает, что модель не поддерживает capability, хотя она есть в конфиге

- **Симптом:** preflight отвергает запрос, например с `vision`, хотя выбранная модель заявлена с этой capability.
- **Причина:** capability должна быть доступна не только в конфигурации родительского LLM router’а, но и в sandbox proxy, который выполняет preflight. Одной успешной проверки прямого HTTP-вызова адаптера недостаточно.
- **Проверить:** debug-лог передачи routing metadata в worker и лог её применения; проверить выбранный tier и capability конкретной модели, а не только общий список capability.
- **Решение:** передавать в worker только безопасные routing metadata (tiers, model IDs и capabilities); сам LLM-вызов остаётся на родительской платформе. Ключи и provider config в worker не передавать.
- **Статус:** передача через IPC реализована; проверено реальным вызовом Agents с картинкой.

## Agents и вложения

### FAQ-AGENTS-001 — PDF или изображение отклоняется до вызова LLM

- **Симптом:** `AGENT_ATTACHMENT_MODEL_UNSUPPORTED` до начала агентского цикла.
- **Проверить:** тип вложения, capability, требуемую подготовку контента и поддержку capability в выбранном tier. Для изображения нужна `vision`; PDF может быть преобразован в текст или в изображения страниц — требования будут разными.
- **Решение:** выбрать модель/tier с необходимой capability и передавать вложение поддерживаемого типа. Не считать факт успешной загрузки файла подтверждением поддержки моделью.
- **Статус:** проверены изображения через VibeProxy; для новых форматов требуется отдельная проверка соответствующего пути подготовки.

## Логи и диагностика

### FAQ-LOG-001 — для диагностики приходится вручную искать процессы и печатать конфиг

- **Симптом:** расследование начинается с широкого `ps`, обхода каталогов или вывода конфигурации.
- **Решение:** включить debug-уровень и искать записи по request ID. Для runtime нужны сведения об источнике CLI/config, выбранном execution backend и worker (`workerId`, PID, путь скрипта, transport), а для LLM — tier/capabilities без секретов.
- **Безопасность:** не логировать API keys, содержимое `.env`, полные provider options, тела запросов или base64-вложения.
- **Статус:** debug-логирование routing metadata и worker startup добавлено; по мере появления повторяемых случаев дополнять FAQ новым ID.
