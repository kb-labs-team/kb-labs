## Task Definition

### Original Request

Спроектировать плагин KB Labs Studio для просмотра архитектурных схем C1–C4, Markdown, DOCX/DOC и PDF. Основной сценарий — видеть KB Labs сверху и проходить по архитектуре от системы к листьям, открывая документы узлов. Нужна работа с папкой документов и преобразование DOCX/DOC в PDF для просмотра внутри Studio.

### Interpreted Goal

Создать переносимый read-only архитектурный пакет и Studio-плагин, который отображает карту KB Labs, поддерживает drill-down по узлам, открывает связанные документы и даёт единое место просмотра офисных файлов и схем.

### Success Criteria

- Пользователь может открыть корень архитектурного пакета и просматривать его внутренние файлы.
- Есть одна карта системы и переходы от контекста C1 к контейнерам C2, компонентам C3 и деталям C4.
- Выбор узла показывает его описание, схему и связанные документы; поддерживаются прямые ссылки на узлы и документы.
- Markdown, PDF, DOCX/DOC и согласованные форматы диаграмм открываются внутри Studio.
- DOCX/DOC конвертируются в PDF с сохранением исходника и возможностью скачать результат.
- Пакет можно переместить между workspace без привязки к абсолютным путям машины.
- Файловый API ограничен зарегистрированными корнями и безопасен к traversal, symlink escape, чрезмерным размерам и недоверенному содержимому.

### Out of Scope первой версии

- Редактирование исходных документов и схем.
- Совместное редактирование, комментарии и review workflow.
- Произвольные внешние URL как источники файлов.
- Изменение исходного кода KB Labs или генерация архитектуры из репозитория.
- Редактор DOCX, DOC или PDF.
- Рендеринг PowerPoint; формат можно добавить позже через тот же интерфейс preview provider.

## Продуктовая концепция

Плагин — это не просто файловый браузер. Главный экран показывает архитектуру KB Labs на выбранном уровне. Пользователь выбирает узел, видит переход к его дочерним узлам, а также связанные схемы и документы. Обычный файловый список остаётся доступным для изучения содержимого экспортированной папки.

Основной путь:

1. Открыть архитектурный пакет KB Labs.
2. Увидеть контекстную карту всей системы.
3. Выбрать систему или подсистему и перейти на уровень ниже.
4. На уровне компонента или листа открыть Markdown, диаграмму, PDF либо офисный документ.
5. Вернуться вверх через хлебные крошки или карту предков.

Навигация по архитектуре должна быть независимой от расположения файлов. Перемещение или переименование файла не должно ломать стабильный ID узла; изменяется только ссылка на документ в каталоге пакета.

## Ключевые решения

### 1. Отдельный plugin `viewer`

Предлагаемое имя сущности — `viewer` (пакет `@kb-labs/viewer-*`), отображаемое название в Studio — **Architecture Viewer** или **Документы и архитектура**. Плагин использует Studio V2 Module Federation, собственную страницу, CLI для управления источниками и REST API для чтения каталога и контента.

Плагин не импортирует Studio internals: UI использует только `@kb-labs/sdk/studio`, build использует принятый в текущем workspace Studio remote tooling, контракты находятся в `contracts`.

Предлагаемая структура workspace-плагина:

```text
plugins/viewer/
  contracts/
  core/
  entry/
    src/cli/
    src/rest/
    src/studio/pages/
```

Конкретный package layout и manifest следует сверить с актуальным шаблоном плагинов при реализации; текущий workspace использует пакеты `contracts/core/entry` и Studio V2.

### 2. Источник — зарегистрированная папка и переносимый ZIP-пакет

У плагина есть список источников. Источник может быть:

- папкой внутри текущего workspace, зарегистрированной локальной CLI-командой;
- ZIP-пакетом, импортированным в разрешённое хранилище workspace или экспортированным из Studio.

Studio не получает доступ ко всей файловой системе машины и не читает произвольные клиентские пути. Зарегистрированная папка ограничивается workspace root или явным разрешением владельца. ZIP импортируется в managed storage, проверяется и раскрывается без выхода из целевой директории. Пакет остаётся обычным набором файлов, пригодным для Git, code review и передачи агенту.

Предлагаемые команды (имена для обсуждения; не существующие команды):

```text
kb viewer source add ./docs/architecture --name kb-labs
kb viewer source import ./kb-labs-architecture.zip
kb viewer source export kb-labs --out ./kb-labs-architecture.zip
kb viewer source list
```

Первая версия — read-only для содержимого источника, но включает экспорт/импорт переносимого ZIP-пакета. Экспорт включает только файлы, разрешённые правилами источника, и сохраняет относительные пути. Импортированный пакет можно заменить новой версией; синхронизация произвольной внешней папки в обе стороны не входит в MVP.

### 3. Каталог архитектуры — отдельный канонический индекс

В корне пакета лежит `architecture.yaml`. Он задаёт дерево узлов, стабильные ID, уровень C4, связи с родителями и список материалов узла. Диаграммы не парсятся для построения дерева: форматы диаграмм слишком разнообразны, а связь по ID в каталоге надёжнее.

Пример предлагаемого формата:

```yaml
schemaVersion: 1
id: kb-labs
title: KB Labs
root: system
nodes:
  - id: system
    title: KB Labs platform
    level: C1
    summary: Extensible engineering platform for teams and coding agents.
    diagram: diagrams/c1-system.mmd
    documents:
      - docs/overview.md
      - docs/decisions.pdf
    children: [developer-platform, studio]
  - id: developer-platform
    title: Developer platform
    level: C2
    parent: system
    diagram: diagrams/c2-developer-platform.mmd
    documents: [docs/developer-platform.md]
    children: [core, sdk, cli]
  - id: core
    title: Core
    level: C3
    parent: developer-platform
    diagram: diagrams/c3-core.mmd
    documents: [docs/core.md]
    children: [plugin-runtime]
  - id: plugin-runtime
    title: Plugin runtime
    level: C4
    parent: core
    documents: [docs/plugin-runtime.md]
    children: []
```

Контракт валидирует уникальность ID, допустимость уровней, согласованность parent/children, существование файлов и отсутствие ссылок за пределы корня. Схема узла опциональна: структура может содержать и документированные листья без диаграммы.

У каждого архитектурного узла есть `evidence`: ссылки на исходные файлы и публичные символы, из которых агент вывел описание. Это позволяет открыть реализацию рядом со схемой и перепроверить утверждение. Evidence — относительный путь и необязательный symbol; номера строк не входят в стабильный контракт.

```yaml
  - id: gateway-auth
    title: Gateway authentication
    level: C3
    parent: gateway
    summary: Handles local and team access modes, credentials, OAuth and user sessions.
    diagram: diagrams/gateway-auth.mmd
    documents: [docs/gateway-auth.md]
    evidence:
      - path: services/gateway/auth/src/service.ts
        symbol: GatewayAuthService
      - path: services/gateway/app/src/auth/middleware.ts
        symbol: registerAuthMiddleware
    children: [gateway-auth-routes, gateway-token-lifecycle]
```

Связь диаграмма → узел реализуется через стабильный node ID в формате диаграммы либо через overlay, описанный рядом с источником. Для MVP приоритетен формат с нативной поддержкой ссылок/кликов; если renderer не выдаёт безопасные node ID, кликабельность обеспечивается отдельной панелью списка узлов диаграммы.

### Связь с product case catalog и intent flow

Viewer не заводит второй каталог продуктовых кейсов. В worktree `g66-casescore` уже описан case-first процесс: продуктовый intent сначала уточняется через case (`docs/qa/scenarios/`), затем от его шагов выводятся тестовые claims и реализация. Там же есть принятая ADR-0050 и 103 сценария `S-…`. Этот каталог остаётся источником пользовательских ожиданий; viewer может связывать архитектурные узлы с case/step IDs и показывать эти связи.

Узел может содержать, например:

```yaml
    caseRefs: [S-255.7, S-045.5]
```

При наличии проверенных ссылок агент может пройти такую цепочку:

```text
user intent
  → matching product cases / exact case steps
  → architecture nodes and relations
  → code evidence, routes, contracts, docs
  → test claims and executed case coverage
```

Для запроса «настроить авторизацию для Gateway» агент сначала использует intent-flow и находит кейсы. Например, `S-255.7` описывает gateway auth перед dispatch к REST/API и MCP; `S-045.5` описывает secured MCP client. Если `caseRefs` уже заведены, viewer находит связанные узлы Gateway, auth gate, REST и MCP. Если соответствие ещё не заведено, агент показывает найденные кейсы и предлагает возможные связи с объяснением и evidence; он не выдаёт догадку за подтверждённое влияние и не меняет каталог автоматически.

`caseRefs` — стабильные внешние ссылки, а не копии case-текста, шагов или статуса. Viewer может проверять, что ID существуют, если case catalog зарегистрирован как источник. Прогресс и надёжность тестирования берутся из существующего `kb qa cases` coverage; наличие test claim без выполненного теста не означает, что путь проверен.

### Стоит ли строить этот слой сразу

Польза реальна для межповерхностных изменений: по одному продуктовому intent агент может найти затрагиваемые подсистемы, обязательные кейсы, архитектурные схемы и тестовые границы. Пользователь видит, почему затронуты, например, Gateway, REST и MCP, и может открыть подтверждающие материалы.

Цена — ручная разметка связей и последующая проверка их актуальности. Устаревший граф хуже отсутствующего: он создаёт ложную уверенность, что влияние полностью найдено. Если начать с привязки всех 103 кейсов, получим заметную работу по поддержке ещё до проверки, сокращает ли это время и ошибки агента.

**Рекомендация:** не строить полный knowledge graph и не размечать каталог целиком для первого релиза. Сначала сделать viewer и карту нескольких важных частей системы. Затем провести небольшой пилот case-to-architecture на Gateway auth: связать `S-255.7` и `S-045.5` с узлами Gateway/REST/MCP и проверить impact-подсказки на нескольких реальных intent-задачах. Расширять модель только если агент стабильно находит нужные компоненты и это экономит пользователю чтение/уточнения.

Для поддержки актуальности:

- product case и его шаги хранятся только в QA catalog; `architecture.yaml` хранит ссылки на ID и короткую причину связи;
- `evidence` указывает на реальные исходники/символы; validator проверяет существование target и case IDs;
- тестовые claims и их PASS/FAIL/NOT RUN берутся из `kb qa cases`, не копируются в карту;
- когда меняется case ID, его шаг или файл из `evidence`, проверка помечает затронутую связь как требующую review; автоматическое переименование/переписывание связей запрещено;
- агент может предложить новые связи в diff, но доказанные/принятые связи попадают в основной impact-результат после review человеком;
- если пилот требует много ручных связей или impact-отчёты шумят, оставить viewer обычным просмотрщиком и отказаться от этого слоя.

### 4. Один renderer contract, отдельные preview providers

UI выбирает provider по MIME/расширению и запрашивает нормализованное описание preview. Начальный набор:

| Тип | Поведение |
|---|---|
| Markdown | Безопасный рендеринг заголовков, ссылок, таблиц и code blocks; локальные ссылки остаются внутри источника. |
| Mermaid | Встроенный интерактивный просмотр с zoom/pan, fullscreen и выбором связанного узла. Основной формат схем агентов для MVP. |
| PDF | Встроенный постраничный просмотр, поиск, масштаб и скачивание оригинала/конвертированного PDF. |
| DOCX, DOC | Серверная конвертация в PDF и просмотр результата; исходник доступен для скачивания. |
| PlantUML/C4-PlantUML | Не блокирует архитектуру; добавить следующим renderer provider после Mermaid, если агентский workflow реально генерирует этот формат. |

Диаграммы остаются текстовыми исходниками в пакете. Рендеринг не исполняет embedded scripts, внешние ресурсы и произвольный HTML. Markdown HTML sanitization и ограничения ссылок обязательны.

### 5. DOCX/DOC → PDF — изолированная server-side операция

REST маршрут запускает конвертацию через интерфейс `DocumentConverter`; конкретный движок скрыт за адаптером. Практичный первый adapter — установленный системный LibreOffice в headless режиме, если он доступен в deployment. Плагин проверяет его наличие и показывает понятную ошибку установки/конфигурации. Нельзя молча обещать конвертацию там, где движка нет.

Конвертация выполняется без shell-интерполяции, в отдельной временной директории, с timeout, ограничениями размера и очисткой временных данных. Кэш ключуется по ID источника, относительному пути и fingerprint входного файла. PDF не записывается рядом с оригиналом автоматически; пользователь может скачать результат отдельно. При замене исходника fingerprint меняется и кэш обновляется.

Старый DOC поддерживается только если выбранный движок его принимает; ошибки и ограничения шрифтов/макросов должны быть отражены в UI. Макросы не исполняются. Конвертер не должен отправлять файлы во внешний сервис.

## UX и навигация

### Главный экран

- Выбор зарегистрированного источника.
- Breadcrumbs текущего узла от корня к выбранному.
- Карта текущего C4 уровня и список дочерних узлов.
- Панель деталей выбранного узла: summary, схема, связанные документы.
- Файловая панель для просмотра остальных файлов пакета.
- Поиск по названиям узлов, путям и Markdown тексту (индексация текста — отдельный MVP+ пункт, в MVP достаточно имён/summary).

### Переходы

- Нажатие на узел схемы ведёт на страницу его ID, если связь определена.
- Выбор дочернего узла заменяет уровень карты и обновляет breadcrumbs.
- Breadcrumb позволяет подняться на любого предка.
- Прямая ссылка имеет устойчивый вид `/p/viewer/:sourceId/node/:nodeId`; файл открывается как `/p/viewer/:sourceId/file/:encodedRelativePath` либо через ID ресурса.
- Неразрешённая ссылка, отсутствующий файл или неизвестный уровень дают страницу с понятной диагностикой и возвратом на родителя.

Схему UI стоит проектировать для большого монорепозитория: карта, детали и список документов должны позволять переключать раскладку и не требовать показа всей глубины одновременно.

## API и модули

Все пути ниже — проектный контракт, не реализованные маршруты. Фактическое объявление должно соответствовать REST manifest текущей версии.

| Метод | Route | Назначение |
|---|---|---|
| `GET` | `/sources` | Список зарегистрированных источников и статусы индекса. |
| `POST` | `/sources/import` | Импорт валидированного ZIP-пакета в managed storage. |
| `POST` | `/sources/:sourceId/export` | Создание ZIP-пакета только из разрешённых файлов источника. |
| `GET` | `/sources/:sourceId/tree` | Валидированное дерево и метаданные узлов. |
| `GET` | `/sources/:sourceId/nodes/:nodeId` | Детали узла, дочерние узлы, диаграммы и документы. |
| `GET` | `/sources/:sourceId/files/*` | Чтение разрешённого файла с MIME, размером и ETag. |
| `POST` | `/sources/:sourceId/convert` | Конвертация DOCX/DOC в PDF или возврат валидного cache hit. |
| `GET` | `/sources/:sourceId/converted/:conversionId` | Поток/скачивание результата конвертации. |
| `GET` | `/health/converter` | Доступность движка и поддерживаемые входные форматы для UI. |

Предлагаемые модули:

- `contracts`: Zod-схемы для source, tree, node, resource, conversion и ошибок.
- `core`: разрешение корня и безопасное чтение файлов, парсер/валидатор `architecture.yaml`, provider registry, cache keys.
- `entry/rest`: тонкие SDK handlers и manifest routes.
- `entry/cli`: source registration/import/list и диагностика конвертера.
- `entry/studio`: библиотека/дерево, архитектурная карта, просмотрщик, toolbar, состояния ошибок.
- `entry/converters`: adapter интерфейс и системный converter; при необходимости вынести в отдельный продукт/service позже.

Плагин не должен зависеть от Studio internals. REST handlers используют `defineRoute` и SDK composables там, где применимо. Внешний converter запускается на сервере плагина, а не из браузера.

## Рабочий цикл coding agent

Архитектурный пакет — обычные файлы в workspace/Git, поэтому агент работает с ним как с частью репозитория. Viewer отображает результат и проверяет структуру; он не становится скрытым хранилищем изменений и не редактирует файлы сам.

### Как агент получает контекст

Пользователь может дать агенту ссылку на источник или узел из Studio либо попросить составить карту по пути репозитория. Команда контекста возвращает машиночитаемый пакет: корень источника, выбранный узел или целевые пути, цепочку родителей, дочерние узлы, прикреплённые документы, соседние компоненты и правила каталога. Для новой карты агент изучает manifests, package metadata, публичные exports, конфигурацию и релевантные тесты. Он не сканирует без разбора весь репозиторий.

Предлагаемые команды (контракт для проектирования, пока не реализованы):

```text
kb viewer source list --json
kb viewer context --source kb-labs --node plugin-runtime --json
kb viewer context --source kb-labs --target services/gateway --task architecture-map --json
kb viewer impact --case S-255.7 --case S-045.5 --json
kb viewer validate --source kb-labs --json
kb viewer link --source kb-labs --node plugin-runtime
```

`context` должен работать и для узла из URL/ID, и для пути в текущем репозитории. Его вывод включает прямую ссылку Studio, чтобы агент мог вернуть её пользователю в итоговом сообщении. Для задачи `architecture-map` пакет контекста указывает ожидаемый scope и проверки evidence, но не подменяет исследование исходников готовой диаграммой. Если traceability-пилот будет успешен, агент сможет выбрать case IDs для intent и запросить через `impact` связанные узлы, точные case steps, evidence и известные test claims.

`impact` — только предлагаемая команда для опционального пилота фазы 4, не требование к первой версии viewer.

### Пример: «сделай карту компонента gateway»

В текущем workspace реализация находится в `services/gateway/`; одноимённые папки `plugins/gateway/` сейчас пусты. Агент должен проверить цель по коду и выбрать service, а не строить карту пустого plugin-каталога.

Ожидаемая декомпозиция:

- **C1:** KB Labs и внешние пользователи/сервисы в контексте платформы.
- **C2:** Gateway как сервис и его основные внешние связи.
- **C3:** app, auth, contracts, core и runtime-server — по реальным пакетам и зависимостям.
- **C4:** ключевые потоки внутри выбранной части, например startup, auth или request routing; не отдельный узел на каждый файл.

Агент изучает `services/gateway/README.md`, package manifests, `services/gateway/app/src/manifest.ts`, публичные exports и профильные тесты. Затем создаёт или обновляет узлы и Mermaid-файлы, добавляет `evidence` со ссылками на исходники и символы, запускает validator и возвращает Studio-ссылку на Gateway. Связи, которые агент вывел косвенно, он явно отмечает как требующие проверки.

Результат — не только картинка: из `Gateway` можно раскрыть `Auth`, открыть схему потока, а затем перейти к реализации и связанным документам прямо из карты.

### Как агент создаёт или меняет архитектуру

1. Проверяет наличие `architecture.yaml`; если пакета ещё нет — создаёт его из шаблона `kb viewer init`.
2. Читает инструкции пакета и контекст родительского узла.
3. Меняет или добавляет документы, Mermaid-схемы и записи узлов обычными файловыми операциями.
4. Сохраняет стабильные ID; при переносе узла обновляет parent/children согласованно и не создаёт дубликаты.
5. Запускает `kb viewer validate --source <id>`. Validator проверяет структуру, уровни C1–C4, локальные ссылки, наличие файлов и запрещённые выходы за корень.
6. Показывает пользователю изменённые файлы и ссылку Studio на узел/документ. Пользователь проверяет визуальный результат и делает обычный Git review.

Плагин не делает автоматический commit или push. Agent changes остаются прозрачными в diff репозитория. Для импортированного ZIP-пакета рабочая последовательность должна распаковать его в выбранную workspace-папку; редактирование скрытой managed-копии не подходит для coding-agent workflow.

### Минимальный package instruction file

В корне пакета рекомендуется поддерживать `AGENTS.md` с краткими правилами авторства: обязательный формат схем, структура уровней, naming/ID convention, команды validate и ограничения на приватные данные. Для первого старта его может создавать `kb viewer init`.

```markdown
# Architecture package instructions

- Keep architecture.yaml valid and update parent/children together.
- Use stable node IDs; do not derive IDs from file names.
- Add only relative paths contained in this package.
- Write diagrams in Mermaid and link diagram node IDs to architecture node IDs.
- Run `kb viewer validate --source kb-labs --json` after changes.
- Do not include secrets, credentials, or personal data in diagrams or documents.
```

CLI-команды в примере станут частью пользовательского контракта только после реализации; их не следует считать существующими командами до scaffold и регистрации manifest.

## Безопасность и эксплуатация

- Источники регистрируются явно. Никаких endpoint вида `read?path=<любой путь>`.
- Все относительные пути нормализуются; проверяется canonical realpath внутри canonical root после разрешения symlink.
- ZIP import защищён от Zip Slip, дубликатов путей, symlink entries, чрезмерного числа файлов и распакованного размера.
- Исключаются `.git`, `node_modules`, `.env`, ключи и скрытые файлы по умолчанию; правила можно настроить на источник с явным подтверждением.
- Ограничиваются максимальный размер файла/пакета, время конвертации, одновременные задачи и объём кэша.
- DOC/DOCX рассматриваются как недоверенный ввод. Макросы не запускаются; converter получает отдельный временный профиль и изолированный temp dir.
- Content-Disposition и MIME задаются сервером; inline отдаётся только для allowlist типов.
- В MVP исходники и каталог не изменяются просмотром. Конвертированные артефакты хранятся в управляемом cache, не в папке проекта.
- Ошибки конвертера не содержат секретные локальные абсолютные пути в UI/логах общего доступа.

## Этапы реализации

### Фаза 0 — Зафиксировать пакет и UX

- Утвердить имя `viewer`, формат ZIP и модель регистрации источника.
- Подготовить начальный `architecture.yaml` для ключевых уровней KB Labs.
- Определить MVP Mermaid node click metadata и прямые URL.
- Проверить deployment-профили KB Labs: где может быть установлен системный LibreOffice и кто управляет зависимостью.
- Утвердить контракт agent context, init и validation CLI, включая JSON-вывод и формат ссылки Studio.
- Не планировать разметку полного QA case catalog. Зафиксировать критерии пилота traceability: точность найденных затрагиваемых компонентов, полезность источников и отсутствие существенных пропусков/ложных связей.

**Выход:** проверенный sample package и пользовательский сценарий без зависимости от реализации UI.

### Фаза 1 — Каталог и навигация

- Scaffold plugin packages в `plugins/viewer` согласно актуальному шаблону.
- Реализовать contracts, проверку каталога и безопасное разрешение путей.
- Добавить CLI регистрацию локальной папки и импорт ZIP.
- Добавить экспорт переносимого ZIP-пакета из Studio и CLI; проверить round-trip import/export.
- Реализовать REST чтение source/tree/node/file.
- Добавить Studio V2 страницу с breadcrumbs, drill-down, файловым деревом и Markdown/Mermaid preview.
- Создать/проверить архитектурный пакет KB Labs и прямые ссылки.
- Добавить `kb viewer init`, `context`, `validate`, `link` и инструкции `AGENTS.md` для пакета.

**Выход:** интерактивный переход C1→C4 по карте, документы открываются в Studio.

### Фаза 2 — PDF и Office conversion

- Ввести `DocumentConverter` adapter contract и health diagnostics.
- Подключить headless converter, изолированную временную работу, timeout и cache.
- Встроить PDF preview, затем DOCX и DOC conversion.
- Добавить загрузку результата и действия «открыть PDF» / «скачать PDF».
- Добавить regression coverage для отсутствующего converter, таймаута и повреждённого input.

**Выход:** пользователь просматривает PDF/DOCX/DOC внутри Studio и получает PDF для скачивания.

### Фаза 3 — Дополнительные форматы и удобства

- Добавить PlantUML/C4 renderer при наличии реальных источников.
- Добавить full-text поиск по каталогу Markdown, закладки и список последних документов.
- Оценить PPTX preview по тому же converter/provider boundary.
- Отдельно спроектировать редактирование, историю версий и save workflow.

**Выход:** расширение форматов без изменения модели источника, каталога или прямых ссылок.

### Фаза 4 — Пилот связей intent → case → architecture (опционально)

- Выбрать один cross-cutting вертикальный срез Gateway auth с кейсами `S-255.7` и `S-045.5`.
- Добавить небольшие явные `caseRefs` к узлам Gateway, REST и MCP с обоснованием и code evidence.
- Научить `validate` проверять ID cases и evidence targets, а Studio — открывать case, схему, код и тестовые claims.
- Проверить на нескольких реальных intent-задачах, получает ли агент полный и полезный список затрагиваемых частей быстрее, чем ручным поиском.
- Продолжать расширение только при подтверждённой пользе; иначе оставить прямые ссылки на кейсы без impact-поиска.

**Выход:** принято решение о масштабировании по пользовательской проверке; пилот не требует переноса или повторной разметки остальных кейсов.

## Проверка результата при реализации

- Contract tests: валидное дерево, битые ссылки, циклы, дубли ID, несуществующие ресурсы.
- Map review: validator подтверждает существование файлов из `evidence`; case IDs дополнительно проверяются только в traceability-пилоте. Точность архитектурных утверждений и связей подтверждается человеком в Studio/Git review.
- CLI contract tests: init идемпотентен, context возвращает ограниченный связанный контекст, validate даёт машинно-читаемые ошибки и Studio link формируется для узла.
- Core security tests: traversal, symlink escape, ZIP Slip, скрытые файлы, лимиты размера.
- Provider tests: Mermaid/Markdown classification, unsupported format, sanitization.
- Converter tests: healthy/missing binary, timeout, bad input, cache invalidation и cleanup.
- Studio E2E: источник → C1 → C2 → C3 → C4 → документ → возврат наверх.
- Manual QA: типичные DOCX/DOC, таблицы, изображения, нестандартные шрифты и крупный PDF.

## Риски

| Риск | Влияние | Решение |
|---|---|---|
| Нет одинакового converter на всех машинах и окружениях | DOC/DOCX функция неожиданно недоступна | Явная converter health/status; adapter interface; описать runtime prerequisite для каждого deployment. |
| C4 карта KB Labs велика и быстро устаревает | Карту трудно читать и поддерживать | Начать с вручную курируемой карты верхних уровней; назначить source of truth узлов; позднее автоматизировать извлечение метаданных из manifests. |
| Диаграммы агентов имеют разные синтаксисы | Сложно поддержать node click и рендеринг | Канонический tree index отдельно от renderer; стандартизовать Mermaid для MVP. |
| Case-to-architecture links устаревают | Impact-подсказка пропускает связанные части или уводит агента не туда | Не размечать весь каталог заранее; проверять изменённые case/evidence ссылки и начать с ограниченного пилота. |
| ZIP/офисные файлы недоверенные | Traversal, DoS или эксплуатация converter | Валидация до обработки, лимиты, отсутствие shell и макросов, sandboxed temp profile. |
| Папки могут содержать секреты и внутренние файлы | Непреднамеренное раскрытие через Studio | Явная регистрация корня и deny-by-default для скрытых/секретных путей. |

## Альтернативы

1. **Только файловый браузер.** Проще, но не даёт надёжной карты системы и переходов C1→C4.
2. **Разбор ссылок только из Mermaid.** Не формирует полную и стабильную иерархию, привязывает навигацию к синтаксису схем.
3. **Конвертация в браузере.** Не подходит для старого DOC и верности макета, создаёт тяжёлую клиентскую нагрузку.
4. **Отдельный сервис конвертации с первой версии.** Чёткая изоляция, но добавляет deployment и service lifecycle до проверки востребованности; начать с adapter в плагине и выделить при необходимости.

## Решения, требующие подтверждения перед реализацией

1. Выбрать окончательную подпись пункта меню: **Architecture Viewer** или **Документы и архитектура**.
2. Подтвердить Mermaid как обязательный формат диаграмм для первого релиза.
3. Подтвердить LibreOffice как рекомендуемый локальный движок DOC/DOCX → PDF для первой версии; при необходимости провести отдельное сравнение self-hosted альтернатив.
