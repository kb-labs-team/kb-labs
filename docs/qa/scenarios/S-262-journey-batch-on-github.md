## User value

A journey maintainer can run the same product-evidence batch locally or on GitHub, identify each result by commit and mode, and retrieve each mode's reports together. Moving heavy runs off the development laptop preserves the evidence needed to review a batch.

## Preconditions

- The repository's journey stack and candidate preparation inputs are available.
- A GitHub runner can check out the selected commit and run Docker-based journeys.
- For a remote run, the local checkout has the configured backup remote and GitHub CLI authentication.

## Steps

| # | Action | Expected |
|---|---|---|
| S-262.1 | Run the in-repository journey batch entry locally and on a GitHub runner for the same commit | Both runs execute the same product-evidence steps: reset, build gate, release-build-output check, candidate preparation, journey unit suite, then local and secured service exploration. On GitHub, one producer performs the shared stages once and publishes the build/candidate input; the local and secured consumer jobs run independently from that input, each with its own timeout, so a failure in one mode does not cancel the other. At most one workflow run is in flight across refs. The local entry uses the same producer and mode stages in sequence. Both environments use the same Compose file list and Verdaccio storage configuration. A Docker image build failure is retried once for that mode; other failures are returned without retry. Each mode artifact contains only its own mode reports and logs, plus the shared stage logs copied into that mode directory. The summary has exactly one final result for pass, failure, or interruption, renders commit and base-ref values as text without shell errors, and the batch metadata records elapsed seconds for reset, build, unit, candidate, each mode, and the whole run. If the affected-build base ref is absent, the entry names the missing ref and the next command `git fetch --all --prune`. Before the hosted batch, `kb-devkit check` verifies that every package selected by the release registry belongs to the live build graph, and reports any package with no build target. A clean shared build produces every release package output, including generated manifests for candidate fixtures; the build stage verifies declared release outputs and fails before candidate preparation with the package and exact build command when an output is missing. Candidate preparation repeats that shared check before packing. Tooling packages without a runtime release output are not included in the release registry. The entry declares shared, local, and secured artifact paths before its first stage. If the entry fails before either mode starts, the shared artifact still contains `summary.md`, `batch-metadata.json`, and `build.log`. |
| S-262.2 | Inspect the batch summary and the reports uploaded for each mode | The run is identified by commit and mode. The build/candidate artifact is named `journey-build-candidate`; the summary artifact is named `journey-shared` and contains `shared/`, `local/`, and `secured/`, with metadata for each mode. The local and secured artifacts are named `journey-local` and `journey-secured`; each contains only that mode's reports and logs plus the shared stage logs, and does not contain the other mode's data. The shared artifact contains root-level stage logs, metadata, and summary even when no mode starts. For a reset/build/unit/candidate failure, `summary.md` names the failing log relative to the shared artifact root; for a mode failure it identifies that mode's `batch.log`. If the publisher cannot authenticate to or write to Verdaccio, it stops before package publication with a clear registry/auth diagnostic and a next command to inspect Verdaccio; it does not emit a per-package 404 cascade. If a journey container exits non-zero, the shared runner saves its complete logs in a named file under `reports/containers/`, and the failure's `Next:` points to that file. The verdict includes the container error or the last available stderr/stdout line so the failed step is visible in the summary. If setup fails before the batch entry writes a summary, the GitHub step summary still succeeds and reports `batch did not start: <failed step>`. Artifact uploads are warning-only when a producer or mode stage produces no files, so available evidence can still be uploaded. |
| S-262.3 | Push a remote batch to a `batch/<tag>` ref and retrieve its artifacts | Pushing the current commit starts the workflow from that ref without requiring the workflow file on the default branch. The checkout fetches the repository default branch, and the affected build uses its `origin/<default-branch>` ref. The harness queries the Actions runs API by branch, pushed SHA, and `push` event, then selects the run whose `path` is the workflow file path; it waits for that run and downloads the shared artifact into `reports/<tag>-shared/` and each mode artifact into `reports/<tag>-<mode>/` before running the existing summary and triage. If the run does not appear within the bounded wait, the harness names the API query as the next command. If the run fails or times out, the harness downloads all available artifacts, then names the run ID and `gh run view` command. Manual workflow dispatch remains available for reruns after the workflow is present on the default branch; its optional baseline input labels batch metadata and does not change the affected-build comparison. |
| S-262.4 | Start a remote batch when the selected commit cannot pass the hosted shared-lane preflight | Before pushing or dispatching, the harness creates a detached worktree at the selected commit SHA under the orchestration root, installs its frozen lockfile with `--prefer-offline`, then invokes the shared-lane owner for the same affected build, release-build-output check, candidate preparation, and journey unit suite used by the hosted workflow. A passing file that exists only as untracked or ignored state in the source checkout cannot make preflight pass; a missing committed input or failure in any shared-lane stage, including candidate release-index sealing, causes the real install, build, candidate, or unit command to fail. The shared kb-devkit cache reuses builds with matching input digests across detached worktree paths; changing an input invalidates that package and its dependents. Failure removes the temporary worktree, preserves the failed check's exit status, names the failed gate, and gives the exact rerun command. A passing preflight may be reused only for the recorded digest of that commit SHA and lockfile. |
| S-262.5 | Retrieve a completed remote batch whose local or secured artifact lacks a scoreboard or container verdict | Batch finalization exits non-zero with an infrastructure error naming each missing per-mode artifact path and the command to rerun the batch. The downloaded artifacts from the selected commit's hosted shared-lane run are incomplete if either mode scoreboard or either mode's container-verdict file is missing or empty; the summary cannot report evidence as complete. |
| S-262.6 | Run `node scripts/ci/remote-verify.mjs <stream> --out <path> [--remote <name>]` from a named agent worktree, or reattach with `node scripts/ci/remote-verify.mjs --attach <verify-ref-or-run-id> --out <path> [--remote <name>]` | The command uses `origin` by default; `--remote <name>` selects another configured GitHub remote. It resolves that remote once, derives the GitHub repository from its URL, and uses the same remote for pushing, looking up, and deleting the unique `verify/<stream>/<timestamp>-<sha>` ref. A missing or non-GitHub remote fails with an actionable diagnostic naming the remote. The `push` trigger starts verification from that commit; the command finds the run by branch, push event, workflow path, and exact `head_sha`, waits for its terminal result, then writes the verdict only to the required `--out` path. Reattachment finds the existing run from the supplied ref or run ID, does not push again, and checks the artifact SHA against the SHA resolved from that ref or the run's `head_sha`. Polling defaults to 45 seconds and stays between 30 and 60 seconds; retries use that same minimum cadence and back off to at most 60 seconds. The bounded deadline, terminal run conclusion, and sustained outage each produce a verdict. The artifact is fetched once after the run completes. The verdict reports each profile stage with failing test names and bounded log tails. After retrieval, the command retries ref deletion; persistent cleanup failure leaves verification status unchanged and adds a diagnostic naming the scheduled sweep fallback. The workflow uses only its default `GITHUB_TOKEN` and receives no laptop environment values. |
| S-262.7 | Run `node scripts/ci/remote-verify.mjs <stream> --out <stream-verdict>` and `node scripts/ci/remote-verify.mjs <stream> --profile candidate --out <candidate-verdict>`, then inspect both runs and artifacts | Each run has a prepare job, one workspace-build producer, an independent test matrix, and a build-dependent test matrix. Only the CI-script suite runs independently while the workspace build is running; the kb-create Go suite, devkit check, package shards, and journey tests run in the build-dependent matrix after receiving producer outputs. The journey-unit suite proves the actual journey runner result is accepted by `qa coverage show`, which retains PASS/FAIL claims and omits BLOCKED claims. The workflow derives `DEFAULT_BRANCH` from repository metadata and passes it explicitly to `KB_DEVKIT_BASE_REF`; stream resolves the merge-base diff in the workflow's full-history checkout even when `refs/remotes/origin/HEAD` is absent, and candidate resolves the empty-tree diff through the same workspace package/dependency graph. A rename across package directories contributes both its old and new paths to the changed-path manifest, so both package owners and their dependents are selected. A changed path not owned by a discovered workspace package selects the full workspace graph, including when mixed with package changes, and the prepare/verdict evidence names the reason as `full: unowned path <path>`; root-only diffs therefore select all packages. Package-only changes still select the changed package and its dependents. Candidate selects every registered workspace package. The producer builds that package set once and passes its outputs to dependent shards. Both profiles run the CI-script suite and bounded workspace-package shards covering every selected package exactly once; the candidate profile also runs the full journey-unit and kb-create Go suites plus the complete devkit check. Every build-dependent shard starts only after receiving build outputs. Build progress remains visible at least every 30 seconds; each sample reports runner memory, workspace-volume free disk, and top RSS processes, and is persisted with a partial stage result during the build. Build concurrency derives from runner CPU and the lesser of the MemTotal budget fraction and MemAvailable, divided by the measured task footprint. If available memory cannot fit one task, capacity measurement fails before the build starts and its stage result includes the typed measurement error code; the workspace build does not impose a per-process Node heap cap below the Node default. If capacity measurement fails, the partial build result records its typed measurement failure (missing meminfo, invalid/missing CPU count, invalid/missing MemTotal, or zero MemAvailable), rather than reporting only a missing build result. Zero MemAvailable is invalid. The verdict records peak memory and minimum free disk, and a terminated build is reported as `runner-shutdown` with its latest resource sample. Each failed workspace build task appears in verdict `failures[]` as its structured package and task plus the first error line from its devkit JSON result; streamed tsup progress does not become a failure entry. Stream fail-fast cancels sibling shards only within the failing matrix; any shard cancelled by fail-fast is `skipped` regardless of whether it uploaded a pass artifact, and the artifact result remains visible as `testsBeforeCancel`. Only failure-level GitHub annotations are failure causes. A failure in one matrix does not cancel other matrices, and the verdict lists all failures. Candidate runs all shards and reports every result. The candidate command pushes one `verify-candidate/<stream>/<timestamp>-<sha>` ref outside the stream push trigger, dispatches exactly one candidate run for that ref and HEAD SHA, attaches only to a workflow_dispatch run matching event, ref, SHA, workflow path, and candidate profile, records `profile: candidate` in the schema-version-1 verdict, and deletes the ref after retrieval; it does not also start a stream run. Stream verdicts record `profile: stream`. The verdict remains schema version 1 and records elapsed milliseconds, status, failures, and the selected package count for the prepare stage, build, and every completed shard. For each planned prepare, build, and matrix job, the verdict passes only when both its stage result artifact and enclosing GitHub job conclusion pass; a non-success conclusion overrides a pass artifact and names the conclusion, failed steps, and annotations. If the job conclusion cannot be read, the verdict names that failure. Prepare covers dependency installation, kb-devkit build, and package selection; a prepare failure includes its named operation and cause; a failed kb-devkit task cause is its structured package, task, exit code, devkit log path, and bounded tail of that failed task's own stdout/stderr; the cause contains no output from passing tasks. The shard-wide log tail is used only when no structured task result exists and is labeled `log-tail fallback:`; a planned shard without a result artifact is reconstructed from GitHub job conclusions, step states, and check-run annotations; runner loss is reported as a named failing job with the annotation, GitHub-skipped jobs are marked skipped, and stream cancellations are marked `skipped (cancelled by fail-fast)` only when a peer in that same fail-fast matrix failed. Failure to fetch GitHub job evidence is itself named in the verdict. Every independent and build-dependent test shard uses the timeout-minutes budget from the verification profile, and a GitHub timeout is reported as timeout with the job name. The devkit task cache key follows the same ownership rule as affected selection. It hashes all tracked files with no package owner once per run and all tracked files owned by each package, including each file's Git-tracked mode, into that package's task keys, including files outside declared task globs such as `tests/**`; a mode-only change such as `100644` to `100755` changes the key without relying on checkout filesystem permissions. A package's task keys also include the tracked content digests of its transitive workspace dependencies, including discovered Go local-replacement edges; thus every changed tracked file invalidates the changed package and every dependent selected by the selector, while unrelated package keys stay unchanged. Modified tracked content is read from the working tree; untracked files do not affect keys. Declared local input globs are redundant for tracked package files; dependency output globs such as `^dist/**` remain inputs for generated files. The outer devkit CAS key only transports a runner-platform cache; task fingerprints decide reuse. Identical immutable task inputs may restore outputs. pnpm and Go module caches remain keyed by their lock/module inputs. |
| S-262.8 | Run a hosted journey batch with an explicit case selection such as `S-010,S-011,S-012,S-014,S-027.1,S-027.2,S-027.3,S-143,S-056`, then inspect its summary and scoreboards | The selection resolves case rows and declared prerequisites from the case catalogue. For each mode, the batch runs exactly the registered runners that own the selected claims in that mode; claims owned only by the other mode are omitted from this mode. If a mode owns none of the selected claims, its output and batch summary state `no selected claims in this mode`; no claim is reported as passing in that mode. A selected claim with no executable registration is refused before any runner starts with an actionable claim-selection error. An explicitly empty `--cases` value is refused with a command to list valid case IDs, and never starts a full batch. Every mode that ran selected claims and the batch summary visibly identify the selected run as partial. Partial evidence is never combined with a full-batch verdict, and batch finalization exits non-zero if any selected-mode scoreboard is partial. A full run without a selection remains the only gating batch. Each mode scoreboard declares the producer-owned Release 1 gate modes (`local`); if the gate declaration is omitted, malformed, empty, or differs from the producer contract, mode gating and finalization fail with an infrastructure error and the summary never reports PASS. |
| S-262.9 | Run the workflow journey when its history checkpoint fails to restart the installed host, then inspect later journey groups | The workflow checkpoint retains its S-056.2 failure and history expectations. Before later groups run, the runner probes the host-running prerequisite again; a healthy shared host is available to unrelated groups, while an unhealthy host remains an explicit prerequisite failure. |
| S-262.10 | Run hosted verification when git reports an authentication or permission denial for the configured repository | The verifier returns `status: "auth"` immediately, names the remote and repository, and directs the maintainer to `gh auth status` and push access; it does not retry. Git push, lookup, and delete operations use the identity provided by `gh`. |
| S-262.11 | Run hosted verification when GitHub's API returns HTTP 403 for missing permission or HTTP 404 for a missing workflow | The verifier returns a typed `auth` or `not-found` status immediately, names the repository, and gives the relevant recovery command; it does not report an outage. |
| S-262.12 | Run hosted verification when git or GitHub returns HTTP 5xx, a connection reset, or a timeout | The verifier retries the transient operation within its configured outage and deadline budgets. |
| S-262.13 | Run the candidate runtime-root tool with a valid candidate index and package tarballs whose recorded URLs use the publisher-side registry address; then run it with invalid preparation inputs | The valid candidate installs from the candidate runtime-root package registry, which is reachable from the runner, while package identity, version, and digest remain those of the candidate index; the publisher-side URL is not fetched. Invalid inputs exit non-zero and write a rendered diagnostic to stderr; the command does not fail silently. |
