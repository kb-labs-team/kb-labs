## Goal

A developer installs a Marketplace entity by the install spec they would type at the Marketplace command. Marketplace resolves it from the KB Registry first, reports the manifest-owned identity and source that served it, and uses npm only as an explicit fallback when the Registry does not own the spec.

## Prerequisites

- [ ] A platform install configured with the Registry URL, its Ed25519 public key and optional auth token through environment references, plus an optional npm fallback URL.
- [ ] A published Commit plugin, a Registry-owned identity, an npm-only fixture identity, and a deliberately tampered Registry mirror response.
- [ ] The installed journey Registry service, its State dependency, and Verdaccio are reachable through their configured service addresses.

| S-268.20 | Resolve packages by short and canonical identity when public and private packages overlap; repeat as anonymous, unrelated authenticated user, owner, and with a share token | Resolution selects only packages the caller can access before deciding whether an identity is ambiguous. Anonymous and unrelated callers receive the unique public match without learning how many private matches exist. A valid share token selects its package. If the caller can access multiple matches, resolution reports ambiguity. A bare stored identity cannot shadow a qualified package's short name. Resolving an exact private canonical identity without access remains the same authorization failure whether one or several private packages match, so Marketplace does not fall back to npm. |
| S-268.21 | Publish version 1 as private and version 2 as public; anonymously inspect package listing, metadata, resolve, stats, and both tarball URLs. Repeat with version 1 public and version 2 private. Also install specs pinned to each exact version, anonymously and as owner. | Visibility belongs to each version. Anonymous reads and resolve expose only public versions, including their matching metadata snapshot; identity resolution also matches the selected version's identity snapshot. A later public version does not expose earlier private tarballs or metadata. A private latest version does not hide an earlier public release from anonymous resolve/list/read. An exact private resolve pin returns 403 and does not fall through to an adjacent public version or npm. An inaccessible private tarball version and a nonexistent version both return `404 VERSION_NOT_FOUND`, without revealing whether the hidden version exists. Stats count only versions the caller can access. The owner can read both versions. Old records do not store historical per-version visibility, so that history cannot be reconstructed. An old version without its own visibility snapshot is treated as private even if the old package-wide flag is public; this fails closed without deleting its metadata or tarball. New releases store their own visibility and metadata snapshot. |
| S-268.22 | Publish a first version, append as its owner and attempt an append as another authenticated namespace; also submit traversal and non-canonical handle, package-name, and version values, then exercise an existing safe legacy package. | The owner can append a new immutable version, while another namespace receives HTTP 403 `FORBIDDEN` with storage and cache unchanged. New handles use the canonical Gateway machine-handle form; package names accept canonical scoped (`@scope/name`) and unscoped npm names with dots, underscores, or hyphens, and versions accept exact valid SemVer including prerelease and build metadata. Invalid traversal or aliases are rejected with HTTP 422 `INVALID_MANIFEST` before queue/storage/cache writes; values are not trimmed or coerced. Safe existing legacy handles and package names remain appendable by their recorded owner. Version storage keys are portable across case-sensitive and case-insensitive filesystems, so SemVer versions differing only by identifier case retain separate tarballs and signatures; existing raw-version storage paths remain readable. Within one Registry process, a simultaneous first publish by two namespaces for the same canonical identity yields one owner and refuses the other; cross-process first-publish coordination requires shared locking or compare-and-swap and is not asserted here.
