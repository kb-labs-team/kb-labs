## Goal

Verify the published launcher can turn the released, sealed V2 index into a
verified platform installation. This is not a source-tree or cache-assisted
test.

## Environment

- [ ] Released `kb-create` binary in `PATH`
- [ ] Node and pnpm supported by the release
- [ ] Empty `PLATFORM_ROOT` and no pre-existing `node_modules` below it
- [ ] Downloaded `release-index.json` from the candidate or stable release
- [ ] `kb-dev` supplied by the release (or an explicit test double only in CI)

## Steps

| # | Action | Expected |
|---|---|---|
| PC-001.1 | Run `kb-create --version` | Prints `kb-create <version>` and exits 0. |
| PC-001.2 | Run `kb-create install --index release-index.json --platform-root "$PLATFORM_ROOT"` in a terminal and complete the displayed prompts; then apply a valid request to a fresh root with the journey's Corepack fixture returning exit code 47 | The terminal prints `Set up KB Labs`, a `Plan: platform <version>, <count> artifacts` summary, `Applying installation…`, then a success/next-step message. A successful install leaves its host running and reachable. The Marketplace install of the scenario plugin may outlast the HTTP client’s former 30-second timeout; kb-create waits for the Marketplace result and reports success when the server completes the install. In secured mode, the first successful human or JSON result contains the first administrator's email and generated password in `firstAdmin.state="disclosed"`; the disclosure marker is recorded only after that result write succeeds. A failure before the result is written leaves the password eligible for the next successful install or apply result. A crash after the result write but before the marker may show the password again on retry. Once the marker exists, later results use `firstAdmin.state="previously-disclosed"`, omit the password, and provide the recovery sequence. Local mode creates no administrator. The operation applies the selected plan; it does not write a request file. The failed apply exits non-zero with `KB_INSTALL_APPLY_FAILED`; its details include `packageManagerExitCode="47"` and `packageManagerStderrTail`, while the full transcript remains in the installer log. |
| PC-001.3 | Run `kb-create plan --index release-index.json --platform-root "$PLATFORM_ROOT" --service-profile default --scenario commit --registry "$REGISTRY" --json` | Exits 0; JSON has `ok: true`, `plan.request.platformRoot` equal to the isolated root, and the resolved `plan.artifacts` and `plan.serviceGraph`; the registry is a valid absolute HTTP(S) URL; no package, generated runtime config, or receipt is written. |
| PC-001.4 | Set `CANONICAL_PLATFORM_ROOT="$(cd "$PLATFORM_ROOT" && pwd -P)"`; run `kb-create apply --index release-index.json --platform-root "$PLATFORM_ROOT" --service-profile default --scenario commit --json` | On success, exits 0; JSON has `ok: true`, `operation: "apply"`, non-empty `receipt` and `logPath`, and `shim: { linked: true, owner: "$CANONICAL_PLATFORM_ROOT" }` when it takes or already owns the shim; `owner` is the canonical installation root regardless of whether the command addressed the install root, `current`, or a physical version root. Marketplace sends install spec `@kb-labs/commit` through the rendered source order, Registry before npm fallback; the receipt records resolved identity `@kb-labs/commit` and the source and version returned by the first source that resolves it. The scenario plugin is absent from release-index artifacts. If the launcher cannot create the `kb` shim, exits non-zero and reports `KB_INSTALL_APPLY_FAILED` with the shim path and filesystem reason; the platform files and receipt remain applied, and the hint gives `kb-create doctor --fix --platform-root "$PLATFORM_ROOT"` as the repair command. A successful host install is left running and reachable. |
| PC-001.5 | Inspect `$PLATFORM_ROOT/current/.kb/kb.config.jsonc`, `$PLATFORM_ROOT/current/.kb/v2/receipt.json`, the install-root entries, the host process record, and `kb-create doctor --json` | The runtime config is valid JSONC, the receipt's service graph contains the selected services, `$PLATFORM_ROOT` is a real install-root directory, `current` is a relative link to a complete version under `$PLATFORM_ROOT/versions/`, shared runtime state and the host process record are under the install root at the paths declared by `platform-layout.json`, and doctor reports the install root, active platform root, versions directory, shared runtime-state directory, and host-state directory. The host process record includes a process identity, and the control token is read from the host-state path doctor reports. The install does not require a separate service-manager file. |
| PC-001.6 | Run `kb-create doctor --platform-root "$PLATFORM_ROOT" --json` after successful install or apply | Exits 0; JSON has `ok: true`, `installed: true`, `running: true`, `reachable: true`, and `platform.ok: true`. |
| PC-001.7 | Set `ACTIVE_VERSION_ROOT="$(cd "$PLATFORM_ROOT/current" && pwd -P)"`; run `kb-create status --platform-root "$PLATFORM_ROOT" --json`, then repeat with `--platform-root "$PLATFORM_ROOT/current"` and `--platform-root "$ACTIVE_VERSION_ROOT"` | Each invocation exits 0 and reports `ok: true`, `installed: true`, `running: true`, `reachable: true`, `host.state: "running"`, and `installation.receiptId` equal to the ID in the active receipt. All three paths identify the same installation and its running host. A recorded host is accepted only when its live process identity matches; a reused PID is reported stale and is never signalled. |
| PC-001.8 | With the installed host running, repeat `kb-create plan --index release-index.json --platform-root "$PLATFORM_ROOT" --service-profile default --scenario commit --json` | The returned plan has the same `planHash`, `artifacts`, and `serviceGraph` as the first plan; planning does not add, change, or remove installation-owned files. Runtime-state paths declared by the kb-create layout contract are outside this comparison. |
| PC-001.9 | While a live KB Labs platform whose root contains spaces and a single quote owns a port required by the selected service graph, run `kb-create apply --index release-index.json --platform-root "$PLATFORM_ROOT" --service-profile default --scenario commit --json`, then execute the suggested stop command | Apply exits non-zero with catalogued `KB_HOST_ALREADY_RUNNING`; the error identifies the owning platform root and PID only after verifying the recorded process identity. Its hint contains a POSIX-shell-safe `kb-create stop --platform-root` command that preserves the exact root when parsed by the shell; executing it stops that platform. A missing, mismatched, or reused-PID process identity returns `KB_HOST_PROCESS_IDENTITY_STALE`, explains why the PID cannot be trusted, and gives a safe record-recovery command without signalling it. For a foreign listener, the command instead returns `KB_INSTALL_PORT_IN_USE`, identifies the owning PID and process command, and provides a shell-safe apply retry command that retains `$PLATFORM_ROOT` and supplies a different `--gateway-url`. |
| PC-001.10 | Set `CANONICAL_A="$(cd "$PLATFORM_ROOT_A" && pwd -P)"`; with root A installed at the release Gateway port 4000 and owning the `kb` shim, apply root B with no `--gateway-url`, then apply a second fresh secondary root C with `--gateway-url http://127.0.0.1:4200` using `install --project-root`; inspect both receipts and run `kb --help`. Plan and update A once each through `$PLATFORM_ROOT_A`, `$PLATFORM_ROOT_A/current`, and its physical `$PLATFORM_ROOT_A/versions/<key>` path; after each plan and update, run `kb-create status --platform-root <same spelling> --json` and record `readlink "$HOME/.local/bin/kb"` | B automatically receives the next free Gateway offset, port 4100, and its receipt records `http://127.0.0.1:4100/health`; its apply result reports `shim: { linked: false, owner: "$CANONICAL_A" }`. C uses port 4200 and its receipt records `http://127.0.0.1:4200/health`; its apply result also reports `shim: { linked: false, owner: "$CANONICAL_A" }`. Each plan and update treats A as the same installation and preserves its Gateway address and single registry row; the following status result reports shim ownership as `{ linked: true, owner: "$CANONICAL_A" }`. The shim target remains byte-for-byte unchanged and `kb` still runs A. |
| PC-001.11 | With root A owning the `kb` shim, uninstall C and then B, each addressed through a different spelling among the install root, `current`, and physical version root; snapshot `readlink "$HOME/.local/bin/kb"` before and after each invocation | Each uninstall exits 0 and its result states `shimAction: "left"` and `shimOwner: "$CANONICAL_A"`; the link bytes do not change, and `kb --help` still runs A. Uninstalling A instead reports `shimAction: "removed"` and removes the link. |
| PC-001.12 | With root A running on the default Gateway port and root B installed with its own Gateway address, run `kb adapter list --json` through root B's direct `kb` command; then stop B and repeat | While B is running, the command reports B's adapter state and never A's, even when A owns the default port. With B stopped, it reports unknown host with the exact `kb-create start --platform-root "$PLATFORM_ROOT_B"` next command, or returns `KB_HOST_IDENTITY_MISMATCH` if A answers B's configured address; it never reports A's state. |
| PC-001.13 | Record the `installationId`, `verification.hostHealthUrl`, service graph ports, and service transport URL ports from `$PLATFORM_ROOT/current/.kb/v2/receipt.json`; run `kb-create update --platform-root "$PLATFORM_ROOT"`, set `ACTIVE_VERSION_ROOT="$(cd "$PLATFORM_ROOT/current" && pwd -P)"`, inspect status using the install root, `current`, and `$ACTIVE_VERSION_ROOT`, then run `kb adapter list --json` through the installed `kb` command | Update exits 0 without restarting the host. The receipt retains the same non-empty `installationId`, Gateway URL, nonzero service ports, and service transport URL ports; each status call reports the old host still serving and the new version pending restart; the CLI command succeeds against that installation. |
| PC-001.14 | Run `kb-create rollback --platform-root "$PLATFORM_ROOT" --snapshot "$SNAPSHOT_ID" --yes`, then run `kb adapter list --json` through the installed `kb` command | Rollback exits 0 and restarts the host. The restored receipt retains the same `installationId`, Gateway URL, nonzero service ports, and service transport URL ports as before update, and the CLI command succeeds against that installation. |
| PC-001.15 | Run `kb-create restart --platform-root "$PLATFORM_ROOT"`, then run `kb adapter list --json` through the installed `kb` command | Restart exits 0. The receipt retains the same non-empty `installationId`, Gateway URL, nonzero service ports, and service transport URL ports, and the CLI command succeeds against that installation. |
| PC-001.16 | With root A already installed at the release Gateway port, apply a fresh root B without `--gateway-url`, stop B, apply root C at `http://127.0.0.1:4200`, then plan a fresh root D and re-plan B | Every nonzero service port in B's service graph and service transport URLs uses B's single allocated 100-port offset. Default allocated Gateway ports remain in the 4000–9900 domain on 100-port boundaries, and all derived service/transport ports stay below the conventional ephemeral range. Stopping B does not release its allocation: C takes the explicit 4200 address, D receives the next 100-port offset, and planning B again retains B's Gateway and service ports. |
| PC-001.17 | Install into a missing target, then into an empty directory; finally try non-empty foreign targets containing an empty or invalid `ownership.json`, a symlinked declared container entry, and a damaged partial installation with an invalid `current` entry | Missing and empty targets install successfully using only entries inside the selected install root; `current` is a relative link to a complete version under `versions/`, and the parent contains no additional entries. Every non-empty foreign target, including one containing only an empty or truncated `ownership.json`, a foreign file under a declared preinstall state path such as `state/scenarios/foreign.json`, a symlink or wrong-typed declared container entry, and a damaged partial installation are refused with `KB_INSTALL_LAYOUT_UNSUPPORTED` before any write; the target and any path reached through a link remain byte-for-byte unchanged. |
| PC-001.18 | Interrupt first install at each ownership-publication boundary and declared layout handoff point, then rerun install; also start two first installs concurrently against the same empty target; repeat each interruption and run uninstall instead | At the ownership-publication boundary, the complete record becomes visible atomically and durably, and only one concurrent install publishes it; the other exits with `KB_INSTALL_OPERATION_IN_PROGRESS`, leaves no staging file of its own, and does not change the winner's target. Any staging file left before canonical publication is refused with `KB_INSTALL_LAYOUT_UNSUPPORTED`, unchanged, with its exact path and an exact manual inspection/cleanup command, even when its contents form a complete valid ownership record; the installer never adopts or deletes it. After canonical publication, the staging name is removed only when it is the same validated record inode with exactly the canonical and staging links. A crash before staging-file creation leaves a fresh target. After canonical publication, retry resumes from the complete owner record. Each retry either completes a healthy versioned install or uninstall removes all installation-owned entries and leaves foreign entries untouched. Recovery of a finalized stage occurs only when its owner identity and in-progress state match the staged receipt, and all declared entries have their contract types. A mismatched owner, completed initial-install state without `current`, extra foreign root entry, symlinked or wrong-typed entry, foreign file under a declared preinstall path without valid provenance, and any damaged partial installation that matches no handoff point remain refused with `KB_INSTALL_LAYOUT_UNSUPPORTED` without changing target bytes. |
| PC-001.19 | Prepare a candidate from the release-index producer, then install it through kb-create's staged candidate installer; repack unchanged package `dist` bytes with changed timestamps and repeat; finally derive a separate sealed index and tarball from the candidate, change one packed `dist` byte while keeping the original provenance, and install into a disposable root | The candidate manifest records every selected package's name, content-derived version, source revision, tarball integrity, and packed `dist` digest. Repacking identical content preserves the version; changing one `dist` byte changes it. Matching package bytes install successfully and the installed `dist` digest matches the sealed provenance. A changed packed package is refused before activation with catalogued `KB_INSTALL_PROVENANCE_MISMATCH`; the diagnostic names the differing field (`identity`, `integrity`, or `digest`), expected value, actual value or explicit missing value with the location checked, the package path, and `kb-dist-digest/v1` for digest comparisons. The disposable root's `current` and `versions/` remain unchanged. Dist symlinks are refused while sealing. Publishing a version already in the registry is refused with the catalogued immutable-version conflict. |

## Pass criteria

No artifact is selected from ambient `node_modules`; configuration and service
metadata come from the published manifests. Any failure has a stable error
code and hint, an operation transcript under `$PLATFORM_ROOT/installer/logs/`,
and a redacted installer dossier under `$PLATFORM_ROOT/installer/diagnostics/`.
Runtime history remains in `$PLATFORM_ROOT/state/logs/` and
`$PLATFORM_ROOT/state/diagnostics/`, exposed through the active version's
`.kb/logs/` and `.kb/diagnostics/` links.
