# 06 — Правила именования команд (DRAFT v0)

> Опирается на существующее: путь команды = `path: 'group subgroup cmd'` (ADR-0015), один манифест = один namespace (ADR-0018),
> системные команды имеют приоритет над плагинными, `operationType: read | mutate | analyze` в манифесте.

## 1. Форма

```
kb <namespace> [<noun>] <verb> [args] [flags]
kb-create <verb> [flags]
```

- **namespace** — область: системная (`project`, `config`, `auth`, `logs`, `plugin`, `adapter`, `health`) или продукт-плагин (`commit`, `mind`, `release`).
- **noun** — сущность из модели понятий (`03-domain-model`), **в единственном числе**: `plugin`, `project`, `adapter`. Опускается, когда namespace и есть сущность (`kb project add`).
- **verb** — только из закрытого словаря (ниже). Новый глагол — через ревью.
- Всё в нижнем регистре, многословные — `kebab-case`, без сокращений.

## 2. Словарь глаголов

| Глагол | Смысл | Пример |
|---|---|---|
| `list` | много, коротко | `kb project list` |
| `show` | одна сущность, подробно | `kb plugin show commit` |
| `add` / `remove` | зарегистрировать / убрать *ссылку* (сам объект не трогаем) | `kb project add ./repo` |
| `create` / `delete` | создать / уничтожить сам объект (delete — деструктивно, ADR-0025) | `kb plugin create my-plugin` |
| `install` / `uninstall` | поставить / убрать пакет-артефакт | `kb plugin install @x/y` |
| `enable` / `disable` | включить / выключить в скоупе | `kb plugin enable commit` |
| `get` / `set` | прочитать / изменить значение | `kb config set llm.model gpt-x` |
| `update` | обновить до версии | `kb plugin update` |
| `run` | выполнить действие продукта | `kb commit run` |
| `status` | текущее состояние | `kb health status` |
| `doctor` | диагностика с рекомендациями | `kb-create doctor` |
| `start` / `stop` | жизненный цикл процесса | `kb-create start` |

Правило пары: `add` ≠ `install`. `add` про то, о чём платформа *знает* (проект), `install` про то, что *ставится* (плагин, адаптер).

## 3. Единые флаги

| Флаг | Смысл |
|---|---|
| `--json` | машинный вывод, один JSON-конверт (как у `kb-create`, ADR-0028) |
| `--project <id\|path>` | проект (по умолчанию определяется по cwd) |
| `--scope platform\|project` | скоуп по ADR-0012 (по умолчанию `project`) |
| `--yes` | не спрашивать подтверждение |
| `--dry-run` | для `operationType: mutate`: показать план, ничего не менять |

`operationType` — один из `read | mutate | analyze | execute` (`execute` разрешён решением автора: запуск действия продукта). Команда с `operationType: mutate` обязана поддерживать `--dry-run` и `--json` (`--dry-run` реестр добавляет сам, `--json` проверяет линт). Деструктивная — протокол ADR-0025.

## 4. Карта: куда какую команду класть

| Команда | Исполнитель |
|---|---|
| `kb-create plan / apply / update / rollback / uninstall / doctor / start / stop / status / wizard` | лаунчер (установка, хост) |
| `kb project *`, `kb config *`, `kb auth *`, `kb logs *`, `kb plugin *`, `kb adapter *`, `kb health *` | клиент хоста |
| `kb <продукт> *` | плагин |
| `reset-admin` | лаунчер, режим восстановления (`kb-create doctor --recover`) ? |

## 5. Что придётся привести в порядок (по текущему коду)

- `marketplace plugins list` → `kb plugin list` (множественное число и лишний namespace `marketplace` убираем).
- Добавить `kb project *` и `kb config get/set` (сейчас только `config show`).
- `auth-reset-admin` уйти из TS-системных команд в лаунчер.
- Псевдоним `kb start/stop/status` → вызов лаунчера (единственный разрешённый алиас, см. `05-executables`).
- Старые имена **не поддерживаем** (решение автора): переименовываем и удаляем без алиасов.

## 6. Как проверять

- Линт манифестов в `kb-devkit`: глагол из словаря, `path` в lowercase/kebab, у `mutate` есть `--dry-run`/`--json`.
- Тест контракта help: все команды, видимые в `kb --help`, соответствуют форме.

## 7. Коллизии и shadowing (по коду `cli/commands/src/registry/`)

**Сейчас три независимых слоя затенения, и все молчаливые:**

1. **Система против плагина** (`service.ts:registerManifest`): если путь плагина попадает в системную команду или *группу*, команда плагина помечается `shadowed` и пропадает. Пишется `warn` в лог.
2. **Владение namespace** (ADR-0018): первый `packageName`, зарегистрировавший верхний сегмент, владеет им; остальные затеняются. «Первый» = по порядку discovery, порядок не зафиксирован правилом.
3. **Один путь из разных источников** (`register.ts`): побеждает источник с большим приоритетом (`workspace` / `linked` / `node_modules`); два `workspace`-пакета с одним путём — ошибка. Затенение логируется только на уровне `info`/`debug`, то есть по умолчанию **невидимо**.

Итог: команда просто «не существует», а причина только в debug-логе.

**Что это значит для новых имён (`kb project`, `kb plugin`, `kb adapter`, `kb config`):**

- Каждый новый системный namespace **резервирует всё под собой**. Если у пользователя стоит плагин, владеющий `project`, то после релиза с системной группой `project` его команды тихо исчезнут.
- Модель «плагины на проект» (ADR-0012, проект выигрывает) вводит четвёртую ось: один namespace у разных пакетов в разных скоупах. Порядок discovery этого не разрешит.

**Правила:**

1. **Список зарезервированных системных namespace** живёт в одном месте в коде и в этом документе; манифест плагина с зарезервированным namespace не проходит линт в `kb-devkit` и отклоняется при `plugin install/enable`.
2. **Затенение — ошибка на этапе установки/включения, а не warn при запуске.** Runtime-затенение допускается только как дрейф состояния и обязано быть видно в `kb health` и `kb plugin doctor`.
3. **Владелец namespace определяется правилом, а не порядком discovery:** скоуп (проект > платформа, ADR-0012), затем явный приоритет; при равенстве — ошибка.
4. **Добавление системного namespace — breaking-изменение:** релизный гейт сверяет его со списком namespace плагинов из `marketplace-registry`.
5. **Namespace плагина = его короткое имя** (`@kb-labs/commit` → `commit`), один к одному; линт проверяет.
6. **Диагностика видна по умолчанию:** любое затенение — одна строка в выводе `kb --help`/`kb plugin doctor` («команда X скрыта: причина»), а не debug-лог.

**Открыто:** `kb plugin *` и `kb adapter *` — системные команды (клиенты хоста) или команды плагина marketplace? Раз системная группа побеждает, а `marketplace` сегодня плагин, его CLI придётся сделать системным.

## 8. Резерв namespace (закладываем сразу, до внешних плагинов)

Резервировать дёшево, отзывать резерв дёшево, занять чужое имя задним числом — ломать пользователей. Поэтому резервируем с запасом.
Один источник истины — файл `reserved-namespaces` в `cli/contracts` (из него генерируется таблица ниже и проверки).

| Уровень | Кто может занять | Имена (стартовый список, ? = сверить с кодом) |
|---|---|---|
| **S — системные** | только ядро CLI | `help` `version` `completion` `diag` `health` `config` `auth` `logs` `webhook` `platform` `project` `plugin` `adapter` `hello`? `groups`? |
| **V — верхнеуровневые глаголы** (на будущее под `kb <глагол>`) | никто, пока не решим | `init` `start` `stop` `restart` `status` `update` `upgrade` `install` `uninstall` `doctor` `login` `logout` `open` `sync` `run` `debug` `test` `build` |
| **F — first-party** | только пакеты скоупа `@kb-labs/*` | `commit` `mind` `agent` `review` `qa` `quality` `release` `workflow` `marketplace` `state` `gateway` `inbox` `steward` `policy` `impact` `devlink` `scaffold` `github` `clickup` |
| **R — резерв под будущие сущности** (только то, что реально планируем) | никто | `user` `team` `tenant` `token` `secret` `env` `skill` `template` `profile` `registry` `deploy` `dev` `devkit` `monitor` `support` `assistant` |

Правила уровней:
- **S, V, R** отклоняются линтом манифеста и при `plugin install/enable`; **F** отклоняется, если пакет не из `@kb-labs/*`.
- Любое имя, начинающееся с `_` или `__`, зарезервировано платформой (сейчас уже так для `__complete`, `__internal`).
- Освободить резерв (V/R → доступно) можно в любой версии; занять резервом (добавить в S/V/R) — только с проверкой по реестру известных плагинов (см. правило 4 выше).
- Стороннему плагину рекомендуем (не требуем) namespace = имя продукта или организации (`acme-deploy`), не общее существительное.

Что это даёт: команды вроде `kb init`, `kb start`, `kb doctor` можно завести позже без коллизий с уже написанными плагинами.

**Не слишком ли агрессивно (решение):** список S/V/F держим полностью, R — только имена, которые реально планируются
в ближайшие ~6 месяцев (сущности из модели понятий, инструменты-бинарники, `support`/`assistant`). Общие технические слова
(`server`, `daemon`, `host`, `cache`, `key`, `service`, `job`, `task`, `tool`) не резервируем: правило 4 (проверка по реестру
известных плагинов перед добавлением системного namespace) защищает от конфликтов и без резерва.
Каждый релиз резерв R пересматривается: имя без планов освобождается. Для авторов плагинов это нормальная цена: `git`, `gh`, `kubectl`,
`docker` устроены так же, а понятная ошибка предлагает замену (`Namespace "user" зарезервирован; попробуйте "acme-user"`).

## 9. Границы применения линтов (решение автора, 2026-09-26)

Правила «платформа только peerDependency» и «без импортов `core-*` в обход SDK» применяются **только к плагинам в смысле автора**: пакетам с манифестом `kb.plugin/3` (поверхности cli/rest/studio) и шаблону плагина. Ядра, демоны, движки и реестры внутри `plugins/` — части платформы и правилами не покрываются.
