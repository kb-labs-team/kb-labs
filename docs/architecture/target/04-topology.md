# 04 — Целевая топология (DRAFT v0)

> Гипотезы помечены `?`. Ответы автора: хост = процесс со всеми сервисами, выбранными при установке; проект идентифицируется по `projectId` (по аналогии с cwd у Claude); режимы различаются в основном эфемерным (транспорт HTTP за абстракцией, аутентификация обязательна, тенантность — да).

## 1. Что показал код (факты)

Каждый сервис устроен одинаково (`shared/daemon/src/daemon.ts`): `runService({appId, defaultPort, setup})` →
`launchPlatform()` → **свой** `PlatformRuntime` → `setup({platform, logger, port, host, projectRoot, platformRoot})`.
Так стартуют gateway, rest, marketplace, workflow, state, mcp. Плюс: единая точка — сервисы уже почти «модули с setup».

Но в коде зашита модель **«один процесс = одно приложение = один проект»**:

| Факт | Где | Следствие |
|---|---|---|
| `launchPlatform` бросает ошибку при попытке запустить второе приложение в том же процессе | `core/runtime/src/platform-launch.ts:343` (`activeRuntime`) | Просто «склеить» шесть `runService` в один процесс нельзя |
| `platform` — process-глобальный синглтон (`Symbol.for('kb.platform')` на `process`) | `core/runtime/src/container.ts:974` | Один набор адаптеров на процесс |
| Конфиг лежит в `globalThis.__KB_RAW_CONFIG__ / __KB_EFFECTIVE_CONFIG__` | `platform-launch.ts:182`, `adapters/config-adapter.ts` | Второй проект с другим конфигом в том же процессе затрёт первый |
| `projectRoot` определяется один раз при старте | `ServiceContext.projectRoot` | Проект — свойство процесса, а не запроса |
| Порты через `KB_NET_OFFSET` + env, транспорт уже абстрагирован (`serviceTransport.listenAddress`) | `daemon.ts:resolveNetwork` | Транспортный шов уже есть — это хорошо |

Вывод: **сложность не в слиянии сервисов, а в том, что проект не является параметром контекста**. Это и есть первопричина
«ставить/запускать под каждый проект» и `--net-offset` руками.

## 2. Классификация сервисов: на машину или на проект

| Сервис | Привязка | Обоснование (по коду) |
|---|---|---|
| **gateway** | машина | маршрутизация, авторизация, единственный внешний порт (ADR-0020) |
| **marketplace** | машина (+ скоуп проекта) | работает от `platformRoot`; проектный lock — параметр операции (ADR-0012) |
| **state-daemon** | машина | KV/state-кэш (ADR-0034), ключи можно префиксировать `projectId` |
| **Studio** | машина | статика SPA |
| **rest-api** | проект ? | `projectRoot`, `core-registry`, исполнение плагинов |
| **workflow** | проект | `projectRoot`, cron-discovery, file-watcher по проекту |
| **mcp** | проект ? | по аналогии с rest |
| **воркеры плагинов** | вызов | изоляция исполнения, уже отдельные процессы/потоки |

## 3. Развилка: как сделать проект параметром

**Вариант A — один процесс, проект в контексте запроса.**
Платформа в процессе одна, проектный контекст (`projectId`, root, конфиг-оверлей, набор плагинов) передаётся через `AsyncLocalStorage`.
Плюс: один процесс на всё, цельность максимальная. Минус: надо вычистить process-глобалы (синглтон платформы, `globalThis`-конфиг, cwd-зависимости)
по всему коду — самая дорогая и рискованная миграция; один проект может завалить остальные.

**Вариант B — машинный хост + лениво поднимаемый рантайм на активный проект (рекомендация ?).**
- **Хост (1 процесс, всегда):** gateway, реестр проектов, marketplace, state, Studio, супервизор.
- **Project runtime (1 процесс на *активный* проект, лениво):** rest/workflow/mcp-модули проекта, собственная платформа и конфиг — как сейчас, без переписывания синглтонов.
- Хост поднимает рантайм проекта при первом обращении, гасит по простою, маршрутизирует по `projectId`.

Число процессов = 1 + число активных проектов, а не сервисы × проекты. Радиус отказа ограничен проектом. Существующие `setup()`-функции
переиспользуются почти как есть: несколько `setup` собираются в один project-runtime вместо шести процессов.
Плата: один дополнительный слой (супервизор + маршрутизация по проекту) и IPC хост↔рантайм (у тебя есть `core-ipc`, и транспорт уже за абстракцией).

**Вариант B → A эволюционно:** если вычистить глобалы позже, project-runtime можно втянуть в хост без изменения внешнего контракта.

## 4. Локальный и облачный режимы

Одна кодовая база, различается конфигурация топологии (как и заметил автор — «в основном эфемерное»):

| | Локальный | Облачный |
|---|---|---|
| Хост | 1 процесс на машине | реплики за балансировщиком |
| Project runtime | ленивый процесс | контейнер/под на тенант/проект (ADR-0037) |
| Транспорт | HTTP/сокет за `IServiceTransport` | HTTP, DNS-discovery |
| Аутентификация | выбирается при установке (с/без); без неё — только loopback | обязательна, полноценная (ADR-0020 identity) |
| Тенантность | да (`core-tenant`); локально один тенант | много тенантов |

## 5. Решения (сжато: по одному варианту, без развилок)

1. **Проект — параметр через рантайм на активный проект (вариант B).** Хост (gateway, реестр проектов, marketplace, state, Studio) + лениво поднимаемый рантайм проекта. Вариант A (чистка всех глобалов) — не сейчас.
2. **Один внешний порт** (`localhost:4000`): `/` — Studio (отдаёт хост как статику), `/api/v1/projects/{id}/…` — проектные API, остальное — внутри.
3. **Внутренний транспорт:** сокеты/named pipes или loopback TCP за `IServiceTransport`. Windows решается реализацией транспорта, а не контейнером.
4. **`projectId` производен от пути.** Перенос папки = «неизвестный проект», добавляется заново; `.kb/` в папке подхватывается штатно. Состояние — `~/.kb/state/<projectId>/`.
5. **Авторизация выбирается при установке.** Без неё только loopback; наружу — только с ней.
6. **Локально — нативные процессы. Контейнер — только облако** (ADR-0037). Локальный «изолированный режим» в контейнере — позже, если кто-то попросит.
7. **Реестр проектов:** `~/.kb/projects.json` (`projectId`, путь, статус, последний запуск).
8. **Состав хоста** задаёт установщик (resolved plan → конфиг хоста).
9. **Конфиг — файл, но руками его никто не пишет.** Три слоя:
   - *Генерируемое* (топология, порты, URL сервисов, пути) — создаёт установщик/хост, пользователь не видит (сейчас `adapterOptions.serviceTransport.services` с `127.0.0.1:5050` прописаны руками в `kb.config.jsonc`).
   - *Выбор пользователя* (адаптеры и их опции, включённые плагины, ключи) — формы в Studio, строятся из `configSchema` манифестов (у адаптеров он уже есть: `adapters/openai/src/manifest.ts`). Секреты — ссылки на env/хранилище, не значения в файле.
   - *Проектные переопределения* — то же в UI, пишутся в `<repo>/.kb/`.
   Файл остаётся источником истины (git, ревью), UI и агент правят его через одну операцию (`config patch` с валидацией по схеме) — как в ADR-0028.

## 6. Вырезаем из первой версии (не проектируем, не поддерживаем)

- Вариант A (проект в `AsyncLocalStorage`, вычистка process-глобалов).
- Локальный запуск в контейнере.
- Несколько хостов/машин, fleet, air-gapped, LTS.
- Мультитенантность в локальном режиме (один тенант).
- Выбор проекта заголовком или сессией — только путь в URL.
- Любые «на всякий случай» режимы аутентификации, кроме «с» и «без».
- Универсальный редактор всего конфига: только адаптеры (выбор + опции + ключи) и включение плагинов; остальное — генерируется или остаётся файлом.

## 7. Что этот разбор даёт по боли автора

- «10 сервисов на проект» → 1 хост + рантайм на активный проект.
- «`--net-offset` руками» → пропадает для пользователя: один порт, остальное внутри.
- «HTTP/сокеты, нет цельности» → снаружи один адрес и понятные пути, внутри хост↔рантайм.
