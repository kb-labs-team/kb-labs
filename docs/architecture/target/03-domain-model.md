# 03 — Целевая модель понятий (DRAFT v0)

## Три крупные сущности (по автору)

| Сущность | Что это | Где живёт |
|---|---|---|
| **Платформа** | ядро, SDK, сервисные модули (gateway/rest/state/marketplace/workflow), Studio | глобально, одна на машину |
| **Продуктовый слой (плагины)** | mind, github, agents, commit, release … | см. «Модель расширений» |
| **Адаптеры** | расширения платформы во внешний мир (LLM, хранилища, логи, транспорт) | реестр платформы, включаются на проект |

Дополнительно: **проект** (регистрируется в платформе), **воркер** (изолированное исполнение плагина).
Агенты и их скиллы — забота плагина `agents`, платформа их не знает и не моделирует.
Разделение адаптеров на «видимые плагину» и «только платформе» уже есть (ADR-0021).

## Три вида состояния

1. **Глобальное** (`~/.kb/`): установленная платформа, реестр проектов, хранилище плагинов/адаптеров.
2. **Декларация проекта** (`<repo>/.kb/`, в git): конфиг, какие плагины/адаптеры и каких версий.
3. **Рантайм-состояние проекта** (вне репозитория): логи, кэши манифестов, lock-файлы рантайма, pid, порты — `~/.kb/state/<project-id>/`.

Декларация = «что должно быть». Состояние = «что происходит сейчас». Сейчас (2026-09) они смешаны в `<repo>/.kb/`: в git status видны `lock.json`, `cli-manifests.json`.

## Модель расширений (развилка, рекомендую гибрид)

- **A. Глобальные, включаются на проект:** одна версия на машину, просто, но конфликты версий между проектами.
- **B. Только локальные на проект:** любые версии, но дублирование на диске и «ставить везде».
- **C. Гибрид (рекомендация):** общее хранилище версий (одна копия каждой версии на машину), проект в lock **пинует** версию и включает. Любые версии сосуществуют без дублирования (как pnpm store / расширения VS Code).
  Условие: плагин объявляет совместимость с версией **SDK-контракта**, установщик проверяет до установки; платформа для плагина — peer, а не зависимость.

## Кто чем владеет и границы

- **Решено:** `workflow`, `marketplace` (и `gateway`, `rest`, `state`) — сервисы платформы. Их CLI-команды подключаются как обычный плагин: сервис в платформе, интерфейс командной строки — плагин-клиент к нему.

- Плагин → платформа только через SDK (`IPluginAdapters`); прямые импорты `core-*` запрещаются линтом.
- Адаптер → реализует порт платформы; подключается по конфигу проекта.
- Проект → не владеет процессами; владеет декларацией.

## Самообновление (важное следствие)

Studio не может установить или обновить платформу, в которой сама работает (и не может поставить себя с нуля).
Поэтому: **тонкая оболочка (App/лаунчер) вне платформы** делает bootstrap, обновление, откат, удаление (движок `kb-create`),
а Studio — основной UI для всего остального и лишь *запрашивает* обновление у оболочки. ?
