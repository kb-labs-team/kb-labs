# 05 — Исполняемые файлы и их роли (DRAFT v0)

> Цель: жёстко зафиксировать, какие бинарники существуют, кто за что отвечает и кто кого вправе вызывать.
> Идея автора: `kb patch` и подобное возможны, только если исполнители разделены явно; Studio не «бегает» в Go-инструменты.

## 1. Инвентарь (по README инструментов, 2026-09)

| Бинарник | Язык | Что делает сегодня | Аудитория |
|---|---|---|---|
| `kb` | TS (Node) | CLI: системные команды (`cli/commands/.../system`), команды плагинов | пользователь |
| `kb-create` | Go | детерминированный лаунчер: `plan/apply/update/uninstall/rollback/doctor/wizard` | пользователь |
| `kb-dev` | Go | локальный менеджер сервисов (процессы, health, порядок старта, watchdog) | сегодня и разработчик, и пользователь (runtime рендерит `devservices.yaml`) |
| `kb-devkit` | Go | сборка/проверки/sync монорепо | автор платформы |
| `kb-deploy` | Go | деплой: build → push → SSH → `docker compose up` | ops |
| `kb-monitor` | Go | read-only статус/логи/health удалённых хостов (после `kb-deploy`) | ops |
| `kb-env` | Go | тестовое окружение: ставит *установленную* платформу через `kb-create` + Verdaccio | автор платформы / e2e |

## 2. Целевые роли (гипотеза, ? = решить)

**Два исполняемых файла для пользователя, остальное — инструменты автора и ops.**

| Роль | Кто | Отвечает за | НЕ отвечает за |
|---|---|---|---|
| **Лаунчер / супервизор** | `kb-create` (переименование в `kb-launcher`? ?) | жизненный цикл установки: install/update/rollback/uninstall/doctor; запуск и остановка хоста, автозапуск; локальный control-канал | любые бизнес- и управленческие операции |
| **Клиент платформы** | `kb` | все команды управления и плагинов; тонкий клиент к API хоста | установка, обновление и удаление платформы |
| **Хост** | процесс платформы (не CLI) | API управления (`config patch`, `project add`, плагины, логи, auth), Studio, маршрутизация | жизненный цикл самой платформы |
| **Инструменты автора** | `kb-dev`, `kb-devkit`, `kb-env` | разработка и тесты платформы | пользовательский путь |
| **Ops** | `kb-deploy`, `kb-monitor` | облачный деплой и наблюдение | локальный пользовательский путь |

Следствие для `kb-dev`: в пользовательском режиме хост — один процесс, супервизора из шести сервисов не нужно.

## 3. Жёсткие правила (что можно проверить)

1. **Studio и хост никогда не запускают бинарники** (`kb-create`, `kb-dev`, `kb` и т.д.) как подпроцессы.
2. **Единственный мост «управление → жизненный цикл»** — узкий локальный control-канал лаунчера (JSON, версионированный):
   Studio → API хоста (`/api/v1/platform/update-request`) → control-канал лаунчера → лаунчер выполняет операцию и перезапускает хост.
   Хост не знает, что лаунчер написан на Go; лаунчер не знает про Studio.
3. **`kb` не содержит логики установки.** Команды вида `kb update` — либо алиас, который *запускает* лаунчер как пользователь (осознанный вход), либо отсутствуют.
4. **Между Go и TS нет общего кода.** Общие только версионируемые контракты: релиз-индекс, receipt, технические манифесты пакетов (ADR-0029), control-протокол лаунчера, HTTP API хоста.
5. **Инструменты автора и ops не входят в установку пользователя** и не вызываются из пользовательского пути.
6. **Один писатель на файл:** установщик пишет только генерируемое (`.kb/generated/…`), `config patch` — только пользовательское.

## 4. Как проверять

- Линт в `kb-devkit`: запрет `child_process`/`exec` на бинарники платформы в `services/*`, `plugins/*/daemon`, `studio/*`.
- Контрактный тест: набор JSON-фикстур control-протокола, общий для Go- и TS-сторон.
- В `README` каждого бинарника — секция «Роль / Не отвечает за» из таблицы выше.

## 5. Решения

- **`kb-env`** — только e2e и тестовые окружения (подтверждено автором). **`kb-monitor`** — только деплой/ops (подтверждено).
- **Переименование `kb-create` не делаем сейчас.** Роль фиксируется документацией и правилами; переименование — churn без выигрыша, вернёмся, если путаница останется.
- **Control-канал лаунчера:** loopback + токен, одинаково на macOS/Linux/Windows. Сокеты/pipes — не вводим.
