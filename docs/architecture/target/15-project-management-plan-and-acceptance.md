# 15 — Управление проектами платформы: план и критерии приёмки

**Статус:** план реализации, не спецификация уже поставленного поведения
**Цель:** дать платформе единый способ подключать, создавать, выбирать и восстанавливать проекты через CLI и Studio, сохранив удобный совместный install для CLI/CI.

Этот документ фиксирует согласованный пользовательский объём, архитектурные ограничения, сквозные сценарии и обязательные изменения документации. Реализацию нельзя считать завершённой, пока критерии ниже не проверены и отчёт по ним не приложен к MR.

## Решения по продукту

1. Установка платформы и проекта поддерживается как вместе, так и раздельно. Раздельный путь нужен для установки платформы с последующим добавлением проектов через UI; совместный путь остаётся удобным для CLI и CI.
2. Новая платформа может работать с пустым реестром проектов. В Studio пользователь добавляет существующие папки или создаёт новый проект.
3. Проект — управляемая сущность с заголовком, описанием, постоянным `projectId` и текущим путём. Пользователь может изменить путь после переноса папки и восстановить запись с устаревшим путём.
4. Studio показывает активный проект в сайдбаре и предоставляет там переключатель. Активный контекст должен быть очевиден на экранах, работающих с проектом.
5. Управление настройками проекта входит в интерфейс проекта. Вкладки плагинов и адаптеров остаются отдельными; Marketplace использует контекст выбранного проекта и не становится новой сущностью или пунктом меню.
6. Команды CLI, выполняемые в проекте, уважают `cwd`. Путь проекта может измениться, поэтому он не является постоянной идентичностью.
7. Нужна отдельная E2E-зона для управления проектами и их интеграции с Host, API, Studio и Marketplace.

## Архитектурные границы и правила реализации

### Установка и жизненный цикл

- Сохранить оба install-сценария: platform-only и platform + project. Удаление или регресс совместного режима не допускаются.
- Создание проекта с новой папкой и подключение существующей папки — разные операции с явной семантикой. Для новой папки пользователь выбирает родительскую директорию и имя/путь проекта; для существующей — указывает саму папку.
- Операции файловой системы и регистрации проекта должны быть в общей доменной операции/библиотеке, используемой CLI и HTTP-слоем. React-компонент и HTTP route не должны содержать самостоятельную логику создания дерева проекта.
- Создание должно быть безопасным при ошибке: не перезаписывать существующие данные; откатывать только артефакты, созданные этой операцией; не удалять пользовательскую папку при обычном unregister.
- Studio получает папки через выделенный Host REST endpoint проектного picker-а. Endpoint возвращает текущую папку и её дочерние каталоги, не возвращает файлы, содержимое или метаданные. Он защищён существующей аутентификацией Gateway и не становится универсальным API чтения файловой системы.

### Идентичность и `cwd`

- `projectId` — постоянный ID записи, не производный от текущего пути после создания.
- Путь — изменяемый атрибут проекта. Обновление пути у существующей записи сохраняет ID, метаданные и привязанное состояние.
- `projectId` создаётся как самостоятельный ID и не выводится из пути. Формат нового реестра строгий; поддержку старого path-derived формата и migration/compatibility layer не добавлять. Обновить все потребители ID: пути состояния, runtime manager, API, кэши и CLI.
- CLI разрешает проект по `cwd` (с учётом вложенных директорий и каноникализации пути). Не вводить обязательное глобальное переключение проекта для обычных команд.
- Заголовок и описание являются пользовательскими метаданными записи проекта. `name` остаётся машинным уникальным alias для CLI; он не заменяет заголовок и описание.

### HTTP, Host, Gateway и Studio

- Studio вызывает REST HTTP API платформы через существующий data-client/base URL.
- Host владеет бизнес-операциями машинного уровня: реестром проектов, созданием/подключением, обновлением пути и восстановлением. Эти операции должны быть доступны даже при нуле зарегистрированных проектов.
- Gateway — сетевой вход/транспортный reverse proxy: auth hooks, forwarding и маршрутизация. Он не владеет бизнес-логикой проекта.
- В текущей топологии Host routes могут быть подключены к внешнему HTTP-входу через Gateway. Это не меняет владение контрактом: описывать интерфейс как REST API платформы, а Gateway — как прокси/транспорт.
- Проектно-зависимые операции несут `projectId` явно в URL/контракте или в другом типизированном параметре. Нельзя молча подменять выбранный Studio-проект проектом runtime по умолчанию.
- Проверить пустой реестр, ошибки неизвестного ID, недоступный путь, некорректное тело запроса и одновременные изменения; возвращать существующий формат ошибок API.

### Marketplace и другие проектные вкладки

- Существующие Marketplace API/операции получают выбранный `projectId` и выполняют установку, включение/отключение и чтение lock/config в корне именно этого проекта.
- Если текущий API требует `projectRoot`, Host разрешает его по `projectId` из реестра; UI не должен самостоятельно отправлять произвольный filesystem path вместо идентификатора.
- Плагины, адаптеры и их экраны остаются отдельными вкладками. При смене проекта их запросы, мутации и кэш должны быть привязаны к новому ID и не показывать/изменять данные предыдущего проекта.

### Качество реализации

- Следовать направлению зависимостей и правилам корневого `AGENTS.md`.
- Без `as any`, `@ts-ignore`, дублирования контрактов, stub-файлов, временных обходов и ad hoc filesystem logic в UI/API.
- Общие контракты, валидаторы и доменные операции переиспользуются CLI и Host API; REST контракт типизирован и валидирует входы.
- Секреты не возвращаются в Studio; конфиги валидируются существующими схемами и сохраняют пользовательские комментарии/формат там, где это поддерживает текущий config writer.
- Регрессионные тесты должны проверять практические границы операций. E2E не должны пропускаться из-за отсутствующего локального сервиса без явного CI fixture.

## Критерии приёмки

Каждый пункт в MR получает статус `PASS` с командой/ссылкой/артефактом проверки либо `FAIL` с описанием дефекта. `NOT RUN` не считается готовым.

| ID | Критерий | Проверяемое свидетельство |
|---|---|---|
| AC-01 | Platform-only install успешен и оставляет реестр проектов пустым; Studio загружается и показывает пустое состояние с действиями «Создать» и «Подключить существующую папку». | E2E + живая проверка Studio |
| AC-02 | Совместный platform + project install остаётся рабочим через CLI/CI; существующие флаги и Action input не ломаются. | E2E установщика и CI Action |
| AC-03 | UI создаёт проект с заголовком/описанием в выбранном месте и подключает существующую директорию с корректной инициализацией. | E2E обеих операций |
| AC-04 | Активный проект очевиден в сайдбаре; переключатель меняет контекст, состояние сохраняется после перезагрузки/повторного запуска согласно выбранной модели хранения. | E2E двух проектов + живая проверка |

| AC-07 | После перемещения/переименования папки обновление пути сохраняет `projectId`, title/description и состояние проекта; старый путь не остаётся активной привязкой. | Registry + Host E2E |

| AC-11 | Реестр и проектный контекст переживают рестарт Host/Studio; постоянный project ID однозначно задаёт путь состояния. | Restart E2E + registry/runtime tests |
| AC-12 | Project picker показывает каталоги Host, позволяет выбрать текущую папку и возвращает корректный абсолютный путь; содержимое файлов и универсальная файловая навигация через API отсутствуют. | Host route + UI tests + живая проверка |
| AC-13 | Есть отдельная CI E2E-зона, которая запускается при изменении project registry/contracts, Host, Studio, Marketplace project scope и собственных фикстур. | Zone resolver/CI matrix evidence |

## Обязательные пользовательские сквозные сценарии

### E2E-01 — Пустая платформа и первое подключение

1. Установить только платформу в чистый временный `KB_HOME`.
2. Запустить Host и Studio; получить пустой список проектов.
3. Подключить существующую тестовую папку с валидным `.kb`.
4. Убедиться, что проект появился в реестре, выбран активным и виден в интерфейсе.
5. Перезапустить Host/Studio и убедиться, что запись сохранилась.

### E2E-02 — Создание новой папки

1. Через Studio открыть project folder picker и выбрать родительскую папку.
2. Задать имя, заголовок и описание проекта.
3. Создать папку, минимальную декларацию проекта и запись реестра через общую доменную операцию.
4. Убедиться, что повторное создание с тем же путём не создаёт дубликат и не перезаписывает данные.

### E2E-03 — Два проекта и переключение контекста

1. Создать/подключить проекты A и B с различными конфигами и наборами плагинов.
2. Переключиться A → B через selector сайдбара.
3. Проверить отображаемый активный проект и данные проектных вкладок.
4. Установить/включить Marketplace entity в B; проверить, что lock/config проекта A не изменился.
5. Переключиться обратно и проверить корректную изоляцию и отсутствие кэшированных данных B.

### E2E-04 — CLI и `cwd`

1. Вызвать проектную CLI-команду из корня A и вложенной директории A.
2. Убедиться, что обе команды разрешили A.
3. Запустить команду вне зарегистрированного проекта и проверить документированное сообщение/поведение.
4. Проверить явный project path/аргумент (если он входит в CLI контракт) и совместный platform + project install.

### E2E-05 — Перенос и восстановление

1. Создать проект и записать его `projectId` и state path.
2. Переместить fixture directory так, чтобы старый path стал недоступен.
3. Убедиться, что UI показывает сломанный путь и предлагает выбрать актуальный.
4. Указать новый путь; проверить сохранение ID, метаданных, конфигурации, Marketplace state и runtime state.
5. Проверить, что старый путь больше не используется.

### E2E-06 — Отказ/ошибка без потери данных

Покрыть отмену picker, папку без прав чтения, существующую непустую целевую папку, невалидный `.kb`, ошибку инициализации, повтор проекта, битый registry, неизвестный ID и конкурентные операции. После каждого отказа сверить файлы, реестр и отсутствие частично созданного проекта.

### E2E-07 — Два режима установки

Прогнать platform-only и совместный platform + project режимы установщика и GitHub Action на временных каталогах. Проверить получившиеся платформу, проектную декларацию и статус; не регистрировать саму папку платформы как проект автоматически, если пользователь явно не выбрал её проектом.

## План отдельной E2E-зоны

- Добавить отдельный `e2e/project-management/ci.zone.json`, который запускает существующий `e2e-studio` suite: его Docker fixture уже поднимает Host, Gateway и Studio, необходимые для проектных сценариев.
- В watch включить реальные существующие исходники: `core/project-registry/**`, контракты project registry, `services/host/app/**`, project runtime, Studio data-client и project UI/sidebar, Marketplace интеграцию и `e2e/project-management/**`. Уточнить пути по фактическому коду при реализации; не добавлять выдуманные glob-пути.
- Подключить suite к поддерживаемому CI workflow/matrix и проверить `scripts/ci/resolve-e2e-zones.mjs` на наборе изменённых путей.
- Запускать реальные HTTP маршруты Host через тот же Gateway ingress, что использует Studio; Gateway остаётся прокси, тестируется именно сквозной REST контракт.
- Изолировать каждое выполнение временными каталогами платформы и проектов; cleanup не должен касаться пользовательского `$HOME` или рабочей копии.

Синхронно заменить решение ADR-0044 о path-derived ID и «перенос = новый проект»; формат старого реестра не мигрировать и не поддерживать. Обновить архитектурные документы `target/03-domain-model.md`, `target/07-migration.md` и реестр открытых/следующих задач. Не оставлять прежние semantics рядом с новым поведением.

Docs проверки: `pnpm --filter @kb-labs/docs-site docs:source-check`, `pnpm --filter @kb-labs/docs-site test`; `docs-audit` — при изменении sitemap/структуры. Проверить очередь staleness на изменённые исходники и убедиться, что ссылки ведут на существующие canonical routes.

## Последовательность реализации и отчётность

1. Инвентаризировать все зависимости от path-derived ID; определить новый самостоятельный ID и строгую схему реестра, затем заменить решение ADR-0044. Старую схему не мигрировать.
2. Зафиксировать REST request/response/error contracts и владельца операций в Host; определить стабильное хранение активного проекта для Studio.
3. Реализовать общие доменные операции (create existing/new, update path, recover, list/get) с атомарностью и проверками безопасности.
4. Подключить Host routes к REST ingress; Gateway только проксирует/маршрутизирует. Добавить contract/integration tests.
5. Реализовать Studio project management, ограниченный Host REST project picker и sidebar selector; проверить project query/cache invalidation и передачу `projectId` в Marketplace/config/plugins/adapters.
6. Сохранить/уточнить CLI `cwd` resolution и оба install режима; добавить регрессионные проверки и обновить Action/CLI docs.
7. Реализовать E2E-зону и перечисленные сценарии; подключить CI.
8. Обновить пользовательские docs, sitemap/source owners и ADR/target docs; выполнить docs checks.
9. Собрать MR как проверяемый пакет: таблица AC-01…AC-15 со статусом и evidence, E2E-01…07 с результатами, CI ссылками, известными ограничениями и оставшимися ручными шагами.
10. Передать пользователю живую Studio для самостоятельной проверки selector, picker, создания/подключения и восстановления проекта. MR не объявлять готовым до этой проверки.

## Вне объёма, если отдельно не согласовано

- Удаление совместного platform + project install.
- Новый верхнеуровневый Marketplace/project plugin menu или копия сущности Marketplace для каждого проекта.
- Произвольное редактирование всех внутренних файлов проекта через универсальный файловый браузер.
- Тихое удаление папок, `.kb` или пользовательских файлов при unregister/recovery.
- Глобальная CLI-команда переключения проекта как обязательный способ работы.
