# 07 — Путь миграции (DRAFT v0)

> Принципы: каждый этап — тонкий сквозной срез, после которого систему можно использовать каждый день; этап можно взять отдельно.
> Ничего не делаем «на всякий случай» (см. вырезанное в `04`). Каждый этап начинается с короткого ADR (список внизу) и заканчивается критерием «готово».
> Оценки не даю: сначала срез 3 проверит модель на реальном коде, потом уточняем.

## Карта этапов

| # | Этап | Даёт пользователю | Зависит от |
|---|---|---|---|
| 0 | Ограждения (guardrails) | ничего видимого; новые ошибки перестают появляться | — |
| 1 | Реестр проектов | `kb project add/list/remove`, проект — сущность | 0 |
| 2 | Хост v0 (один порт) | `localhost:4000`: Studio + gateway + marketplace + state в одном процессе | 1 |
| 3 | Рантайм проекта | проектные сервисы (rest/workflow/mcp) лениво, по `projectId`; конец `--net-offset` руками | 2 |
| 4 | Лаунчер-супервизор | `start/stop/status` хоста, control-канал, обновление с перезапуском | 2 |
| 5 | Конфиг: слои и команды | `kb config get/set`, генерируемое отдельно от пользовательского | 1 |
| 6 | Studio как основной UI | проекты, плагины, адаптеры (формы из `configSchema`), health, «Обновить» | 3, 4, 5 |
| 7 | Модель расширений | общее хранилище версий, пин в проекте, проверка версии SDK | 3 |
| 8 | Оболочка-мастер (.exe) | установка и онбординг без терминала | 4, 6 |
| 9 | Первая польза | плагин коммитов «из коробки», «создай свой плагин» | 6 |
| 10 | Общая проверка и e2e-контур | доказательство, что весь путь пользователя работает и не ломается | 0–9 |

Этапы 4 и 5 можно вести параллельно с 3. Этап 7 — самый рискованный: отдельный срез, не блокирует 1–6.

## Этап 0 — Ограждения

Цель: новые нарушения границ не появляются, пока идёт остальное. Кода поведения не меняем.

- Файл `reserved-namespaces` в `cli/contracts` + проверки (линт манифеста в `kb-devkit`, отказ при `install/enable`) — `06-command-naming`, §7–8.
- Линт границ: плагины не импортируют `core-*` в обход SDK; `services/*`, `studio/*`, `plugins/*/daemon` не запускают бинарники платформы (`child_process` на `kb`, `kb-create`, `kb-dev`) — `05-executables`, `docs/ARCHITECTURE-BOUNDARIES.md`.
- Линт: платформа — `peerDependency` плагина, не `dependency` (закрывает баг с транзитивной платформой на будущее).
- Единый конверт ошибки и каталог кодов (`08-errors`): схема в `contracts`, общие Go/TS фикстуры, линт «код есть в каталоге и имеет hint». Каждый следующий этап добавляет в каталог свои коды до релиза.
- Индекс `docs/architecture/README.md` и две строки в `AGENTS.md` «начни отсюда».

Готово, когда: линты в CI, существующие нарушения либо исправлены, либо в явном списке исключений с датой.
Риск: шум от существующих нарушений (список в `ARCHITECTURE-BOUNDARIES.md`) — вводим со списком исключений, не «красным».

## Этап 1 — Реестр проектов

- Библиотека реестра (`core`): `~/.kb/projects.json` (`projectId` от пути, путь, статус, последний запуск); `projectId` → каталог состояния `~/.kb/state/<projectId>/`.
- Команды по правилам `06`: `kb project add | list | show | remove`. Пока работают напрямую по файлу (хоста ещё нет); позже станут клиентами хоста, интерфейс тот же.
- `project add` на папке с `.kb/` подхватывает её; без `.kb/` предлагает инициализацию (декларация, `03`).
- Рантайм-состояние проекта начинает писаться в `~/.kb/state/<projectId>/`, а не в `<repo>/.kb/` (логи, кэши манифестов, lock рантайма) — уходит шум из git status.

Готово, когда: два проекта зарегистрированы, `kb project list` их показывает, в `git status` проекта нет рантайм-файлов.
Риск: код, который читает кэш/логи по старым путям (`.kb/cache/cli-manifests.json`, `.kb/logs`) — нужен список мест.

## Этап 2 — Хост v0

Срез, который проверяет модель на реальном коде.

- Один процесс `kb-host` = один `launchPlatform` (одно приложение) + `setup()` модулей **gateway, marketplace, state, studio-static** (все машинные, `04` §2). Сервисы остаются пакетами; меняется точка сборки, а не их код.
- Порт один (`4000`): `/` — Studio (gateway отдаёт статику), `/api/v1` — gateway. Внутреннее — через `IServiceTransport` (loopback/pipes).
- Проектные сервисы (rest, workflow) пока запускаются как сейчас отдельными процессами для одного активного проекта — цель этапа проверить хост, а не всё сразу.
- Режим авторизации «с/без» как свойство установки: без — только loopback (`04` §5).

Готово, когда: одна команда запускает хост, Studio открывается на `localhost:4000`, marketplace и state работают через хост, порты 3000/5070/7777 больше не нужны снаружи.
Риск: `launchPlatform` не допускает второе приложение в процессе, `platform` — process-синглтон (`04` §1). Хост должен быть *одним* приложением; модули не вызывают `runService` заново, а регистрируют `setup()` в общем хосте. Проверяется первым же прототипом.

## Этап 3 — Рантайм проекта

- Хост поднимает **один процесс на активный проект** (rest, workflow, mcp — модули проекта) лениво, по первому обращению, и гасит по простою. Адрес рантайма регистрируется в транспорте динамически.
- Маршрутизация по пути: `/api/v1/projects/{id}/…` → рантайм проекта (`04` §5).
- `--net-offset` и ручные порты уходят из пользовательского пути (остаются только у `kb-dev` для разработки платформы).

Готово, когда: два проекта одновременно, у каждого свой рантайм, плагин коммитов работает в обоих через один порт.
Риск: динамические адреса в `serviceTransport`, жизненный цикл рантаймов (утечки, зависшие процессы), нагрузка при десятках проектов — лимит активных рантаймов.

## Этап 4 — Лаунчер-супервизор

- `kb-create` получает `start | stop | status` хоста, автозапуск, control-канал (loopback + токен, `05`).
- `update`/`rollback` останавливают и перезапускают хост; `doctor` различает «установка» и «платформа» (`05` §карта).
- Хост больше не запускается через `kb-dev` в пользовательском режиме; `devservices.yaml` в пользовательском режиме заменяется конфигом хоста.
- `reset-admin` переезжает в `doctor --recover`.

Готово, когда: `kb-create start` поднимает всё, `update` без ручных шагов, `kb-dev` не нужен пользователю.

## Этап 5 — Конфиг: слои и команды

- Разделение: генерируемое (`.kb/generated/`, пишет установщик) и пользовательское (`kb.config.jsonc`, пишет `config set`), `04` решение 9.
- `kb config get | set | show`, атомарная запись + блокировка файла; валидация по схеме.
- Схемы для секций конфига платформы (сейчас строго валидируется только `ExecutionConfig`); у адаптеров `configSchema` уже есть.
- Топология и URL сервисов (`adapterOptions.serviceTransport.services`) выводятся из плана установки, из ручного конфига пропадают.

Готово, когда: новый проект настраивается без ручного редактирования JSON: адаптер, ключ LLM, плагины.

## Этап 6 — Studio как основной UI

- Экраны: проекты (`+ Add project`, переключение), плагины/адаптеры (включить, форма опций), health/doctor, «Обновить» (через API хоста → control-канал лаунчера).
- Каждое действие — вызов той же операции, что и CLI-команда (`04`/`06`: клиент хоста).
- Studio ничего не запускает и не пишет в файлы сам (правила `05`).

Готово, когда: цикл «добавил проект → включил плагин → настроил адаптер → увидел статус» проходит без терминала.

## Этап 7 — Модель расширений

- Общее хранилище версий плагинов/адаптеров на машину; в проекте lock пинует версию и включает (`03`, вариант C).
- Плагин объявляет версию SDK-контракта; установщик и хост проверяют совместимость до установки/загрузки.
- Платформа для плагина — peer; в рантайме одна копия (ограждения из этапа 0 + проверка при загрузке).
- Правила namespace: владелец по скоупу, затенение = ошибка при установке (`06` §7).

Готово, когда: два проекта на разных версиях одного плагина работают одновременно; несовместимый плагин отклоняется при установке.
Риск: самый высокий — затрагивает discovery, marketplace, resolve модулей (`ADR-0012`, `ADR-0030`). Делать отдельным срезом.

## Этап 8 — Оболочка-мастер

Скоуп сейчас: «сел и поехал» для узкого круга. Подпись кода, нотаризация и публичные каналы обновления — отложены (см. `01-north-star`, «Отложено»).

- Тонкое приложение (`.exe` / `.app`) поверх JSON-протокола `kb-create` (ADR-0028): мастер (режим, набор модулей), прогресс, трей, автозапуск.
- Логики установки в оболочке нет.

Готово, когда: пользователь без терминала доходит от скачивания до открытого Studio.

## Этап 9 — Первая польза

- Плагин коммитов включён на добавленном проекте; в Studio — «Создать свой плагин» (шаблон `templates/plugin-template` + помощь агента плагина `agents`).
- Критерий из `02`: ≤5 минут от установки до первого полезного результата.

## Этап 10 — Общая проверка и e2e-контур

Финальный этап: не новая функциональность, а доказательство, что цель из `01-north-star` достигнута и держится. Использует существующий контур (`e2e/` зоны, `e2e/CI-ZONES.md`, `e2e/PLUGIN-MATRIX.md`, `kb-env`, `reusable-launcher-e2e.yml`, `kb-create-install-action-smoke.yml`); новые сценарии добавляются только там, где их не покрывает существующее.

- **Сквозной сценарий пользователя на чистых машинах** (Windows, macOS, Linux): установка → запуск хоста → `+ Add project` → плагин коммитов даёт первый результат → второй проект и переключение → обновление → откат → удаление. Критерии из `01-north-star`: ≤5 минут от установки до первой пользы; дни подряд без ручного вмешательства.
- **Сценарии сбоев** по каталогу `08-errors`: мёртвый хост, занятый порт, неверная авторизация, битая установка, несовместимый плагин, устаревший лаунчер. Проверка: каждый сценарий даёт ожидаемый код ошибки, подсказку и рабочее действие восстановления (снапшот-тесты вывода в терминале и Studio).
- **e2e по зонам, где нужен:** лаунчер и супервизор (`start/stop/status`, control-канал, обновление с автооткатом); хост и gateway (`/` Studio, `/api/v1`, режимы «с/без авторизации», отказ при выставлении наружу без авторизации); несколько проектов одновременно (рантайм на проект, изоляция состояния, лимит активных); модель расширений (два проекта на разных версиях плагина, отказ по несовместимому SDK, затенение имён); Studio в браузере (Playwright) — проекты, плагины, адаптеры, health, «Обновить»; безопасность локального UI (Origin/Host, токен сессии).
- **Совместимость и релиз:** матрица совместимости на трёх ОС (R4.2), репетиция релиза до canary по расписанию (R5.1; публикует в реальный канал, только по явному разрешению автора), замер времени релиза против цели ≤20 минут.
- **Бюджеты:** холодный старт хоста, память хоста и рантаймов на N проектов, время `checks`; пороги фиксируются и проверяются в CI.
- **Регрессия архитектуры:** линты границ и именования (этап 0) без новых исключений, ни одного бинарника платформы, запущенного из хоста/Studio, каталог ошибок без кодов без подсказки.
- **Приёмка:** чек-лист «автор пользуется ежедневно» на своих проектах в течение оговорённого срока; все пункты `?` в `docs/architecture/target/` закрыты, документы переведены из DRAFT и слиты в `docs/architecture/`.

Готово, когда: сквозной сценарий зелёный на трёх ОС в CI, все сценарии сбоев проходят, бюджеты соблюдены, приёмка автора подтверждена.

## Сквозные правила

- Каждый этап обновляет соответствующий документ в `docs/architecture/target/` и переводит его из DRAFT в фактическое состояние (после миграции `target/` сливается в `docs/architecture/`).
- Этапы 2, 3 и 7 — проверка гипотез на коде; если срез 2 покажет, что модель B не работает, возвращаемся в `04`, а не «дожимаем».
- Не делаем: вариант A (`AsyncLocalStorage`), локальные контейнеры, fleet/air-gapped/LTS (см. `04` §6).
- Релизы платформы — только по процессу `release-prepare` и с явного разрешения автора (`CLAUDE.md`).
