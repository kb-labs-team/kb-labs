The QA case catalog in `docs/qa/scenarios/` is the source of truth for product
flows. Tests claim the steps they verify, and run results determine whether each
step passed. Coverage is not declared in case frontmatter.

## Validate cases and claims

```bash
kb qa cases list
kb qa cases validate
```

`validate` checks frontmatter, step ids, and test claims. Each step uses its
case id followed by a stable number, such as `S-010.4`. Journey steps declare
`cases=["S-010.4"]`, Playwright test titles include `@S-020.3`, and Go or
Vitest tests put `// case: S-023.2` directly above the test.

## Generate coverage

The JSON output is the machine-readable coverage source used by local release
checks and the generated matrix below. Refresh the matrix after case or test
claim changes with:

```bash
mkdir -p .kb/qa
kb qa coverage show --level all --mode local --json > .kb/qa/case-coverage-local.json
kb qa coverage show --level all --mode secured --json > .kb/qa/case-coverage-secured.json
node scripts/generate-qa-case-coverage-docs.mjs
```

To enforce the release level, include a run result produced by a journey or test
runner:

```bash
kb qa coverage show --level release --mode local --run .journey/reports/service-local.json
```

The JSON schema is versioned as `kb.qa-case-coverage/v1`. Each applicable step
reports `PASS`, `FAIL`, `NOT RUN`, or `NOT COVERED`; cases outside the selected
install mode report `NOT REQUIRED`. Release coverage passes only when every
active release case passes all of its steps with an executed journey or e2e
claim. Unit claims alone do not satisfy a release case.

Projects can keep their catalog elsewhere by setting `qa.casesPath` in their
plugin configuration. The default is `docs/qa/scenarios`.
