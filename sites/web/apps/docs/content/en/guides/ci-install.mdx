Most workflows only need a thin slice of the platform — a release job needs the `release` plugin, not the gateway, workflow engine, or marketplace. V2 `kb-create apply` and the `kb-create-install` GitHub Action make that slice explicit while using the same release-index contract as the human wizard and agent protocol.

## `kb-create apply`

A non-interactive command that applies exactly the plugins/services you name — no wizard, no default footprint beyond the platform baseline.

```bash
kb-create apply --index ./release-index.json \
  --request-platform-root ./ci-platform \
  --project-root "$GITHUB_WORKSPACE" \
  --plugins=release
```

The index digest and compatibility matrix are validated before any package is
written. An unknown plugin, missing provider, incompatible version, or missing
platform/SDK/binary relation fails during planning with structured diagnostics.
The same request can be passed unchanged by CI, an agent, or the wizard.

### Pin versions

Append `@version` to any plugin or service ID:

```bash
kb-create apply --index ./release-index.json --plugins=release@0.2.0 \
  --services=rest@1.4.0 --request-platform-root ./ci-platform
```

Omit the version to install `@latest`. Pins are independent per catalog (plugins and services are separate maps), since an ID like `marketplace` can exist in both.

### Select an SDK or Platform release

`kb-create` has two selectable axes in the shared index (today every release publishes both at one version): the SDK (`@kb-labs/sdk`) and the Platform
(core packages, adapters, services, plugins, and service companion CLI
packages). Select a channel on either axis, or pin it to an exact version:

```bash
# Track the next platform train while keeping the default SDK channel.
kb-create apply --index ./release-index.json --plugins=release \
  --platform-channel=canary --request-platform-root ./ci-platform

# Reproduce a known platform release exactly.
kb-create apply --index ./release-index.json --plugins=release \
  --platform-version=2.118.1 --request-platform-root ./ci-platform
```

Supported channels are labels in the sealed release index. On an
axis, `--*-version` and `--*-channel` are mutually exclusive. A channel is
resolved to a concrete version before installation, then recorded in the
installation state so `kb-create status` can show what actually landed.

The release index carries the shared platform/SDK/binary compatibility matrix.
It is checked before packages are written; an incompatible or incomplete
relation stops the command. Production has no compatibility bypass.

### Configure adapters

Adapters back the capabilities plugins declare (`llm`, `storage`, `cache`, ...). Wire one explicitly with `--adapters`:

```bash
kb-create apply --index ./release-index.json --plugins=release \
  --adapters "cache=@kb-labs/adapters-redis@0.3.0" \
  --request-platform-root ./ci-platform
```

Role names are validated against the platform's canonical capability list — a typo'd role fails before any package installs. Most common roles (`llm`, `storage`, `logger`, `analytics`, ...) already have a sane default wired from the manifest catalog. Cache consumers can use the built-in StateBroker adapter without provisioning Redis, or select `@kb-labs/adapters-redis` for a shared external cache. If a plugin declares a capability as required and nothing backs it, planning fails before any package installs.

### Agent protocol and package manifests

Agents can discover available scenarios without knowing launcher internals:

```bash
kb-create agent scenarios
kb-create agent inspect --scenario commit
kb-create agent plan --scenario commit \
  --project-root ./project --platform-root ./ci-platform
```

CI installation itself remains scenario-free and deterministic. Technical
metadata can be resolved directly from exact package artifacts or registry
specs instead of being copied into the installer:

```bash
kb-create agent plan --scenario commit \
  --package-dir ./node_modules/@kb-labs/commit-entry \
  --manifest-cache ./.kb/manifest-cache
```

Package manifests are the source of truth for requirements, adapter
capabilities, and non-secret provider defaults. Scenario manifests describe
user intent; they do not contain complete `kb.config.jsonc` documents.

## Reusable GitHub Action

For GitHub Actions workflows, `.github/actions/kb-create-install` wraps the binary download and the flags above into one step:

```yaml
- uses: kb-labs-team/kb-labs/.github/actions/kb-create-install@main
  with:
    release-index: ./.kb/release/release-index.json
    plugins: release@0.2.0
    platform-dir: ${{ runner.temp }}/kb-platform
```

| Input          | Description                                                            |
| -------------- | ---------------------------------------------------------------------- |
| `plugins`      | Comma-separated plugin IDs, each optionally `@version`                 |
| `services`     | Comma-separated service IDs, each optionally `@version`                |
| `adapters`     | Comma-separated `role=pkg[@version]` pairs                             |
| `platform-dir` | Where the platform installs to (default: a runner temp dir)            |
| `registry`     | Override the npm registry (e.g. a local Verdaccio for testing)         |
| `release-index` | Required sealed `kb.create.release-index/v2` file for the release train |
| `version`      | Pin the `kb-create` binary release; use an exact tag in production |

Outputs: `platform-dir` (resolved install path) and `config-path` (generated `kb.config.jsonc`), for chaining into later steps that need to `cd` into the platform or read its config.

The action downloads the `kb-create` binary directly from GitHub Releases and
applies the supplied release index — no separate install script step is needed.
